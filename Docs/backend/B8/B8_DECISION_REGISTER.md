# B8 — Decision Register

> `CLASS_A_UNRESOLVED = 0`. Every Class A decision below has an enforcement artifact and acceptance evidence.
>
> **B8-FIX.1 note:** `B8-D-A021` was added after an independent CTO audit found the original pack's entitlement-override precedence rule ambiguous under adversarial testing (multiple simultaneous active overrides for one `(workspace, code)` had no combination rule). It is assigned the next unused Class-A identifier rather than reusing the already-explained gap at `B8-D-A010` (§`B8_ACCEPTANCE_TESTS.md`/`B8_VERIFICATION_MATRIX.md` history) — `A010` remains permanently unused and is not repurposed, to avoid semantic confusion between an unrelated historical numbering note and this genuinely new decision.
>
> **B8-FIX.2 note:** `B8-D-A022` was added after a fresh independent re-countersign found that `B8-D-A021`'s cardinality/precedence fix, while itself correct, left a materially separate question unanswered: what does a metered override resolve to *after* the workspace's base plan changes (upgrade or downgrade)? `A021` is about how many override rows may exist and how one combines with the base at the moment of resolution; `A022` is about what "the base" means when it has moved since the override was granted. Assigned the next unused identifier (`A010` remains unused, per the note above; `A021` is not overloaded with an unrelated concern).

| `B8-D-A021` | How many `EntitlementOverride` rows may be simultaneously effective for one `(workspace, code)`, and how do a boolean-capability override and a metered-quota override each combine with the base plan result? | **At most one** active, unexpired override per `(workspace_id, code)` — enforced by a `status` column plus a partial unique index `(workspace_id, code) WHERE status='active'` (never a `now()`-based index predicate). `grant_capability` is an absolute grant (`allowed := true`, legal only with `value=true`). `extend_quota` stores an **absolute limit value** (never additive/stacking), legal only when `value` strictly exceeds the plan's current limit at grant time or is `null` (unlimited) — see `B8-D-A022` for how that stored value is resolved against a *later-changed* base. A concurrent replacement grant transactionally revokes the prior active row before inserting the new one. A corrupt state with >1 active row for the same code (unreachable through any governed command) fails closed (`LOCKED`/`EXHAUSTED`, `500 INTERNAL_ERROR`, alerted) rather than summing/maxing/latest-wins | independent audit found the original wording ("an active, unexpired override row") assumed uniqueness the schema didn't enforce — a genuine, implementation-blocking gap (brief §10's "resolve precedence explicitly" requirement). Absolute stored value (not additive) directly closes the audit's own stated risk ("avoids accidental quota stacking"); single-row enforcement is what makes replacement-not-addition safe | `B8_ENTITLEMENT_MODEL.md` §5, §5a, §5b, §5c; `B8_STORAGE_MODEL.md` §`entitlement_overrides` persistence pattern + lifecycle; `B8_CONCURRENCY_MODEL.md` C11–C12 | `AT-B8OVR-1`…`10` (§`B8_ACCEPTANCE_TESTS.md`) |
| `B8-D-A022` | A metered override's stored value is absolute and frozen at grant time; what is the effective limit once the workspace's base plan subsequently changes (upgrade or downgrade)? Does a stale override ever reduce what an upgraded plan would otherwise grant? | **No.** Effective limit is recomputed on every resolution as `MAX(current_base_limit, override.value)` — never the override value applied unconditionally, and never `base + override`. `current_base_limit` is always the freshly-resolved step-4 limit against the workspace's *currently effective* `PlanVersion`/trial, recomputed on every resolution, never a value cached at grant time. An unlimited override (`value IS NULL`) always dominates. A plan-version change (upgrade, downgrade, trial conversion, or a catalog-only `PlanVersion` publish that doesn't move the subscription) never rewrites, revokes, or requires re-validating the override row itself — only the read-time computation changes what the stored value resolves to | independent re-countersign (`AUD-MAJ-2`) found the original `B8-D-A021` wording ("absolute replacement of the limit... the step-4 limit is replaced by value") applied the override's frozen value unconditionally, silently capping an upgraded plan below what it should grant — a genuine contradiction with `B8-D-A014`'s "never restrict below plan" and an implementation-blocking gap no document resolved | `B8_ENTITLEMENT_MODEL.md` §5b, §5b-i; `B8_UPGRADE_DOWNGRADE_MODEL.md` §8; `B8_CONCURRENCY_MODEL.md` C13 | `AT-B8OVR-11`…`18` (§`B8_ACCEPTANCE_TESTS.md`) |
