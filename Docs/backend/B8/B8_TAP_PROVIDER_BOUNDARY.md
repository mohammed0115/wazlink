# B8 — Tap Payments Provider Boundary

> Design only. No Tap credentials, SDK calls, or provider code are implemented in B8. This document records **official Tap Payments facts** gathered from `developers.tap.company` on 2026-09-01, classifies each fact's confidence, and states its impact on B8's provider-neutral domain model. Where the official documentation does not establish a behavior, it is marked `UNRESOLVED` rather than invented, per this phase's authoring brief §5.

## 1. Purpose and scope

`B8_PAYMENT_PROVIDER_PORT.md` defines the provider-neutral `PaymentProviderPort` (the name is inherited verbatim from frozen `BACKEND_INTEGRATION_BOUNDARIES.md`, which already names `PaymentProviderPort`/`Tap Payments` as the Billing/Payments integration boundary). This document is the **Tap-specific adapter boundary** behind that port: it records what Tap actually is, so the adapter can be implemented later without the implementer re-deriving provider facts from scratch, and so B8's domain model never leaks a Tap-specific concept upward.

No fact below is a secret, credential, or sandbox key. No fact below authorizes coding Tap; `BACKEND_TIMEOUT_POLICY.md` already reserves Tap's timeout budget (connect 3s / request 20s / job 5m) and `BACKEND_INTEGRATION_BOUNDARIES.md` already names the port; this document supplies the missing provider-contract detail those two files deferred.

## 2. External validation register

Format: `OFFICIAL_SOURCE | FACT | B8_IMPACT | CONFIDENCE | STATUS`. Every row's source is `developers.tap.company` (Tap's own documentation site), fetched live during authoring, and re-fetched live during `B8-FIX.2` remediation (2026-09-01) for `B8-X-005`/`B8-X-012` specifically. `CONFIDENCE` is `HIGH` (explicit, unambiguous prose or schema on the official page, or cross-validated across two independent fetches of the same page returning consistent detail), `MEDIUM` (stated but with a gap, a genuine cross-page inconsistency, or a single AI-summarized page whose exact wording could not be block-quoted), or `LOW` (inferred/partial). `STATUS` is exactly one of `VERIFIED` (the fact is established from official documentation, at the row's stated confidence), `PARTIAL` (the core fact is established, but a specific, named sub-detail remains genuinely unresolved or inconsistent across official sources), `UNRESOLVED` (official documentation does not establish the fact at all), or `CONTRADICTED` (official documentation states something that conflicts with a prior B8 assumption — none of the 15 rows below currently carry this status). A `PARTIAL` or `UNRESOLVED` row is a fact B8 must not assume beyond what is stated and must gate behind provider-contract validation before implementation, consistent with B0's own `REQUIRES PROVIDER CONTRACT VALIDATION` marker on Tap status mapping.

Only **one** row now carries `STATUS = UNRESOLVED`: `B8-X-014` (webhook endpoint configuration precedence and delivery-ordering guarantees) — official documentation simply does not address this question at all, unlike `005b`/`012` where a real, narrower gap remains inside an otherwise-established fact. The three original Class B items (`B8-D-B002`, `B8-D-B003`, `B8-D-B010`) remain the correct pre-implementation gate for `B8-X-005b`/`012`/`014` respectively — `PARTIAL` still means "do not code against this detail without a final check," the same posture `REQUIRES PROVIDER CONTRACT VALIDATION` always described, just now scoped to a narrower, named gap for two of the three items instead of the whole fact. None of the three blocks B8's architecture, because every non-`VERIFIED` row is isolated to the **adapter's internal mapping table**, never to a domain concept: B8's Subscription/Payment/UpgradeQuote state machines, RBAC, tenancy, and API contracts are fully specified without needing Tap's exact numeric code table, exact recurring-charge wire format, or webhook-endpoint precedence resolved first.

### Structure vs. exact codes (`INFO-1` clarification)

Two distinct things are true at once, and the table above is written to keep them separate rather than blur them:

1. **Structure is settled, frozen-B8 architecture, and does not require Tap reconfirmation**: the provider-neutral status set (`created/pending/authorized/captured/failed/cancelled/partially_refunded/refunded`, `B8_PAYMENT_PROVIDER_PORT.md` §3), the fail-closed rule for any unrecognized provider status (maps to `pending` plus a mandatory reconciliation flag, never silently to `captured`/`failed`), and the domain consequence of every §2 fact (e.g., "a renewal is always a new, auditable `Payment`," `B8-X-012`) are B8 architecture, decided now, and stable regardless of what a later Tap sandbox check finds.
2. **Exact Tap-side codes/shapes still need reconfirmation before coding**: only the *specific numeric-code-to-category assignment* in `B8_PAYMENT_PROVIDER_PORT.md` §3's table (which `000`/`100`/`301`/etc. map to which of the 8 structural statuses), the *remaining refund-code-count discrepancy* (`B8-X-005b`), and the *two named wire-level details* of a merchant-initiated recurring charge (`B8-X-012`) are what `REQUIRES PROVIDER CONTRACT VALIDATION` actually gates — not the structure itself, which is unaffected by whatever that reconfirmation finds. A future adapter implementer re-validating `B8-X-005a`/`005b` against a live Tap sandbox and finding, say, that code `304` behaves differently than described here would update only the mapping table, never the fail-closed structural rule that table plugs into.

No provider fact is invented to fill this gap — where §2 could not establish a code-to-category mapping with full confidence, it is marked `MEDIUM`/`LOW` and the mapping is flagged for reconfirmation rather than asserted as certain.

## 4. Non-invention statement

No HMAC header name, algorithm, endpoint path, field name, or status code in this document was invented; every one is cited to a fetched `developers.tap.company` page or a search snippet directly quoting one, per the rows above. Where the fetched page used an AI summarizer rather than returning raw HTML the confidence is marked `MEDIUM` rather than `HIGH` (unless cross-validated across two independent fetches, per `B8-X-005a`), and the exact wording should be re-fetched and block-quoted before implementation. Where a fetch could not fully reconcile a detail — the refund-code row count (`B8-X-005b`) and the `customer_initiated` type/`threeDSecure` inconsistency between Tap's own two recurring-charge pages (`B8-X-012`) — the row is marked `PARTIAL` and only the confirmed core is asserted; no code, field name, or behavior is filled in by guessing.
