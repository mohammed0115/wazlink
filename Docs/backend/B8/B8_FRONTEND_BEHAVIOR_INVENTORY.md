# B8 — Frontend Behavior Inventory

> Frontend evidence only. No frontend file is modified by B8. Frozen frontend reference: `30bc15e9ca3c0205df2b49e792fce1b8e78a36b1` (same reference every prior phase used). Evidence root: `client/src/`.

## 1. Method

Mechanical inventory of every billing/plan/entitlement/checkout/usage/trial behavior in `client/src`, excluding `Docs/legacy-react-mockup` and `Docs/NOMO_V1_PROMPTS_ARCHIVE` (archives, not live frontend). Every behavior below is individually itemized with an `FB-B8-###` ID, exact source file, exact line range (verified by reading that range), observed behavior, B8 interpretation, and whether it requires a real backend contract. Classification:

- **A** — needs a real backend contract
- **B** — product/UI behavior (informative, not itself a contract)
- **C** — frontend-only presentation
- **D** — mock/prototype placeholder, non-authoritative

No frontend mock state is treated as backend authority (per the authoring brief §2); Class A rows are the only ones that directly shape a B8 architecture decision, and every such decision is cited back to its `FB-B8-###` row elsewhere in this pack.

### `B8-FIX.2` remediation note

An independent audit (`AUD-MAJ-3`, `AUD-MAJ-4`) found that only 26 of the previously-claimed 78 behaviors (19 Class A + 7 reclassified Class B) were individually itemized with a row; the remaining 52 existed only as un-ID'd prose summaries ("24 additional behaviors" / "16 presentation behaviors" / "12 mock behaviors"), and five `FB-B8-###` IDs cited by other B8 documents (`FB-B8-021`, `FB-B8-023`, `FB-B8-030`, `FB-B8-040`, `FB-B8-042`) did not exist anywhere in this file — a sixth, `FB-B8-036`, was falsely claimed as "spot-checked present" in `B8_VERIFICATION_MATRIX.md` §4 without ever being defined or legitimately cited anywhere in the 36-file corpus.

This revision re-derives every behavior directly from `client/src` (not from the prior prose summary) and gives each one its own row. Methodology:

1. The 19 Class A rows and 7 reclassified Class B rows from `B8-FIX.1` are **carried over unchanged** (content and IDs) — they were independently re-verified against source during this pass and remain accurate.
2. The prior condensed Class B/C/D prose was mined for every named behavior it gestured at (e.g. "sidebar/nav lock badges", "4-step checkout wizard", "Arabic label maps"); each was located in source, read in full, and given a real row.
3. Every frontend file plausibly in scope was re-read in full or by targeted section (`Billing.tsx`, `Checkout.tsx`, `Onboarding.tsx`, `Dashboard.tsx`, `Sidebar.tsx`, `Topbar.tsx`, `Settings.tsx`, `Discovery.tsx`, `Automation.tsx`, `DiscoveryModal.tsx`, `DiscoveryResults.tsx`, `EntitlementGate.tsx`, `shellNavigation.ts`, `entitlementService.ts`, `upgradeProjection.ts`, `dashboardProjection.ts`, `onboardingService.ts`, all `contracts/*.ts`, `domain/data.js` billing section, `domain/types.ts`, `s11-billing.css`, `payment-checkout.css`) to confirm no additional distinct billing/entitlement behavior was missed.
4. The five legitimately-cited orphan IDs (`FB-B8-021`, `-023`, `-030`, `-040`, `-042`) were matched to real, distinct evidence matching what their citing document actually describes, and are **reused** at their original numbers for citation continuity — no citing document needed a text change, since each citation's description was already factually accurate; only the missing row was the defect.
5. `FB-B8-036` corresponds to no real citation anywhere in the corpus (checked by full-corpus grep) and is **not reused** — inventing a row for it would be fabrication, not remediation. `B8_VERIFICATION_MATRIX.md` §4 is corrected accordingly (see that document).
6. `FB-B8-003` — cited by `B8_PLAN_CATALOG.md` and `B8_TRIAL_MODEL.md` as "the frontend's `mockModel.plans` fixture" but likewise never defined here — is reused for the same reason as the five above.
7. Every other new behavior is assigned a fresh sequential ID starting at `FB-B8-075` (the lowest unused number after the highest previously-defined ID, `074`), grouped by class, in the order discovered during the file-by-file pass. No gap in the old numbering (e.g. `002`, `008`–`011`, `015`, `016`, `018`, `019`, etc.) is reused for a new behavior — those numbers were never assigned to anything and are retired unused, same as `036`.
8. Two behaviors described identically in more than one source location (e.g. "current plan name" rendered in Sidebar, Topbar, and Dashboard) are merged into **one** row citing every location, per the corpus's own duplicate-elimination rule — never split into near-identical rows. `FRONTEND_DUPLICATE_BEHAVIORS = 0` (verified: no two distinct rows describe the same product-level behavior without a stated reason in Notes).
9. **`B8-FIX.2a` hygiene note.** Three further files sit in the module graph immediately behind the sources item 3 names but were not separately listed there: `services/index.ts`, `services/data.ts`, `services/mock/legacyDataBridge.ts`. All three were inspected (independently re-inspected under `B8-FIX.2a`) and found to be thin pass-through/delegation wiring — every exported member either re-exports or directly delegates, with at most a trivial default-value fallback (e.g. `services/index.ts`'s `startCheckout()` defaulting to the catalog's first plan when no `planId` is supplied), to a function already sourced from `domain/data.js` (already itemized, e.g. `FB-B8-003`/`FB-B8-054`/`FB-B8-103`) or already covered by the typed `BillingService`/`EntitlementService` shapes itemized at `FB-B8-048`/`FB-B8-070`. None contains a distinct product-level behavior warranting its own row under item 8's merge discipline. No new `FB-B8-###` ID is assigned for these three files; they are recorded here as inspected-and-classified wiring, not omitted from scope.

This produced a **real, re-verified count of 62** distinct behaviors — lower than the previously-claimed 78. The gap is explained by the prior document's condensed prose bundling multiple adjectives/clauses into what looked like a larger count than the source actually supports once each item is traced to real code and duplicates (e.g. the same plan-name label shown in three places) are merged rather than counted three times. No behavior described in the original prose was dropped; every named item was traced to source and either became its own row or was merged into an existing one, with the merge reason stated in Notes.
