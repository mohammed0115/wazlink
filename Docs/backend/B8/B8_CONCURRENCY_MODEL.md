# B8 — Concurrency Model

> Design only. Adopts the frozen concurrency primitives (`B1_CONCURRENCY_IDEMPOTENCY.md` §1) verbatim: integer `version` + `If-Match`, `SELECT ... FOR UPDATE`, partial unique indexes, deterministic lock ordering, `transaction.atomic` before distributed locks. Redis is never used for any decision below.

## 1. Race table

| # | Race | Mechanism | Authoritative outcome |
|---|---|---|---|
| C1 | Two simultaneous upgrade attempts against the same `UpgradeQuote` | frozen: quote row lock + `status=active` check + partial unique index on `upgrade_quotes.payment_id` | first consumer wins; second gets `409 CONFLICT` (or `QUOTE_ALREADY_CONSUMED` if it re-reads after the fact) |
| C2 | Two concurrent `CreatePayment` calls against the **same subscription**, different quotes | `SELECT ... FOR UPDATE` on `subscriptions` row for the duration of quote-consumption (`B8-D-A012`) | first acquires the lock and proceeds; second sees an in-flight payment and returns `409 CONFLICT` (reason `payment_in_progress`) |
| C3 | Upgrade + cancellation racing | `subscriptions` row lock; whichever command commits first wins; the loser re-reads current `version` and either applies cleanly (cancellation after a completed upgrade; upgrade after a pending cancellation, which clears `cancel_at_period_end` per `B8_UPGRADE_DOWNGRADE_MODEL.md` §7) or is rejected as stale (`409 STALE_VERSION`) if it was holding an outdated `version` | deterministic, no last-write-wins |
| C4 | Upgrade + downgrade racing | same row lock; an upgrade's success always clears any `pending_plan_version_id` (§`B8_UPGRADE_DOWNGRADE_MODEL.md` §7) | explicit supersession, not silent overwrite |
| C5 | Webhook + user-initiated action (e.g., cancel arrives while a renewal webhook is processing) | `subscriptions` row lock inside `ProcessPaymentWebhook`; the webhook only ever advances `Payment`/period fields, never touches `cancel_at_period_end` | independent fields, no contention — both can commit without conflicting, since neither writes the other's field |
| C6 | Webhook + reconciliation processing the same Payment concurrently | `payments` row lock inside both `ProcessPaymentWebhook` and `ReconcilePayment`; both apply the identical legal-transition check (§`B8_WEBHOOK_MODEL.md` §6) | whichever acquires the lock first wins; the second sees the already-updated status and no-ops (idempotent) |
| C7 | Two provider events for the same Payment arriving out of order | legal-transition check rejects any backward move | order-independent convergence (§`B8_WEBHOOK_MODEL.md` §6) |
| C8 | Admin override grant + a live provider update to the same subscription | `subscriptions`/`entitlement_overrides` are separate tables with independent locks; a concurrent `SubscriptionActivated`/plan change and a concurrent `GrantEntitlementOverride` touch disjoint rows, so no write-write conflict is possible between them — entitlement resolution simply reads whichever committed state exists at evaluation time | no conflict by construction between these two specific tables |
| C9 | Two workspace members invoking `CancelSubscription` simultaneously | `Idempotency-Key` differs per request (different principals), so both could technically race the `subscriptions` row lock | row lock serializes them; the second sees `cancel_at_period_end` already `true` and returns the same success response (idempotent at the domain level, not just the header level) |
| C10 | Quota reservation racing subscription downgrade taking effect | `usage_counters` row lock is independent of `subscriptions` row lock; a reservation reads the limit **at the start of its own transaction** — a downgrade that commits between the read and the reservation is not applied retroactively to a request already in flight (no phantom mid-request limit change); the *next* request sees the new limit | deterministic, transaction-snapshot-consistent |
| C11 | Two concurrent `GrantEntitlementOverride` calls for the **same** `(workspace_id, code)` (`B8-D-A021`) | if a prior `active` row exists, both transactions attempt `SELECT ... FOR UPDATE` on it — the row lock serializes them, and the loser proceeds only after the winner's revoke+insert commits, then performs its own revoke(-already-revoked, idempotent no-op)+insert cycle; if **no** prior row exists (both are racing to create the *first* grant), the partial unique index `(workspace_id, code) WHERE status='active'` is the backstop — the loser's `INSERT` fails the unique constraint and is mapped to `409 CONFLICT` (reason `override_already_active`) | exactly one `active` row exists after both transactions resolve; never two, never zero (unless a subsequent legitimate revoke) |
| C12 | Two concurrent `RevokeEntitlementOverride` calls against the same row | first acquires the row via its `UPDATE ... WHERE status='active'`; the second finds `status` already `revoked` and returns the identical success response if it is an idempotent replay of the same request, else `409 CONFLICT` (reason `override_not_active`) | idempotent-safe, no double-revoke side effect |
| C13 | A plan-version transition (`SubscriptionActivated` upgrade, `ApplyScheduledDowngrade`, trial conversion) committing concurrently with an `EntitlementDecision` resolution for the same workspace (`B8-D-A022`) | Resolution is read-only and holds no lock — it reads whatever `subscriptions.plan_version_id`/`entitlement_overrides` state is committed at the start of its own transaction (read-committed snapshot), computing `step4_limit` fresh every time (`B8_ENTITLEMENT_MODEL.md` §5b-i), never reusing a value from a prior resolution or from override-grant time | resolution deterministically reflects either the fully-pre- or fully-post-transition committed state, never a partial one; because `step4_limit` is always freshly read, `MAX(step4_limit, override.value)` can never yield a result older/lower than the last-committed base — the transition and the read cannot interleave into an inconsistent intermediate value, since neither writes to a row the other holds mid-transaction |

## 2. Deterministic lock ordering

Any command touching both `subscriptions` and `usage_counters` (none does directly in Phase 1 — quota reservation is always the *reserving domain's* transaction, never Billing's own) would lock `subscriptions` before `usage_counters` to prevent deadlock, per `B1_CONCURRENCY_IDEMPOTENCY.md` §1's "deterministic lock ordering" primitive — recorded here for completeness even though no Phase-1 B8 command currently needs both locks in one transaction.

## 3. What is forbidden (inherited verbatim, `B1_CONCURRENCY_IDEMPOTENCY.md` §5)

No Redis lock for any Billing/Entitlement decision. No advisory lock where a row lock suffices. No optimistic retry loop that silently re-applies a command the client did not re-authorize. No last-write-wins on any domain field — every field-level conflict above resolves through an explicit rule (version check, supersession, or independent-field non-conflict), never "whichever request happened to commit last, arbitrarily."
