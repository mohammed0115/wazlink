## What B8 found before designing anything

B8 is unusual among this corpus's phases in how much of its skeleton frozen B0 already laid down before B8 existed to fill it in: the `PLAN-`, `SUB-`, `UPQ-`, `INV-BILL-`, `PAY-`, `TAX-`, and `WHR-` public-ID prefixes were already registered; `Plan`, `UpgradeQuote`, `Payment`, `Invoice`, `TaxInvoice`, and `EntitlementDecision` DTOs were already frozen with required-field lists; the `UpgradeQuote` price-snapshot, single-consumption mechanic was already fully specified down to its transaction boundary; the Subscription (`trialing→active→past_due→suspended`, `active→cancelled→expired`) and Payment (`created→pending→authorized→captured`, with refund branches) state machines were already named; and B1, B3, B4, B5, and B7 had each independently deferred a specific numeric or policy question to "B8" by name, anticipating this phase's existence. B8's task was therefore predominantly **specifying and hardening an already-anticipated skeleton**, in the same spirit B6 and B7 both recorded for their own phases — not inventing one from nothing.

## What B8 designed

The full Phase-1 architecture for: **Plan Catalog** — `Plan` plus a newly introduced `PlanVersion` (immutable price/capability/limit snapshot, closing the one genuine gap frozen B0 left: nothing previously prevented editing today's catalog from retroactively repricing an existing subscription). **Entitlement resolution** — a five-step deterministic precedence algorithm (workspace state → subscription lifecycle deny-floor → grace → trial-or-plan → override-broadens-only) producing a closed internal result, projected onto the frozen `EntitlementDecision`/`UsageDTO` transport shapes with three additive optional fields. The override step is itself fully deterministic (`B8-D-A021`, added in `B8-FIX.1`): at most one active override may exist per `(workspace, code)`, enforced by a `status` column plus a partial unique database index rather than a time-based predicate; a boolean override is an absolute grant, a metered override stores an absolute limit value (never additive/stacking); and a corrupted state with more than one active row fails closed rather than summing, maxing, or picking one. **Its interaction with a later plan change is likewise fully deterministic** (`B8-D-A022`, added in `B8-FIX.2`): a metered override's effective limit is always `MAX(current_base_limit, override.value)`, recomputed fresh on every resolution against the workspace's *currently effective* `PlanVersion`/trial — never the override's grant-time value applied unconditionally — so an upgrade past a stale override value is honored immediately, a downgrade never silently erases a still-active override, and no override row is ever rewritten by a plan-version change. **Usage/quota** — the `usage_counters`/`usage_ledger` schema and the transactional-reservation pattern every metric-owning domain (B1's `seats`, B7's `automationRuns`, and now B4's `aiAnalyses`, B2's `leads`, B3's `discoveryRuns`) follows identically. **Trial** — fully mechanism-designed, deliberately shipped inactive pending a Product Owner policy call the frozen corpus explicitly reserved. **Upgrade/downgrade/cancellation** — upgrade is immediate on confirmed payment; downgrade is always next-period and never destructive; cancellation is cancel-at-period-end only in Phase 1, with immediate hard-cancel explicitly deferred. **Checkout/payment** — no new `Checkout` aggregate is introduced (the frozen `UpgradeQuote`+`Payment` pair already covers it); `payment_attempts`, `refunds`, and `billing_customers` — three tables B0 named but never detailed — are fully specified. **Provider boundary** — a provider-neutral `PaymentProviderPort` (name inherited verbatim from frozen `BACKEND_INTEGRATION_BOUNDARIES.md`) behind which Tap's actual, officially-researched API contract lives (authentication, charge/refund/customer/webhook/idempotency mechanics, and — critically — Tap's own documentation confirming redirect success does not prove payment, which independently corroborates B0's pre-existing "webhook-first truth" doctrine). **Webhook and reconciliation** — B8 does not reinvent the frozen Webhooks-domain inbox; it specifies the Billing-specific consumer behind it, including the exact Tap `hashstring`/HMAC-SHA256 authenticity mechanism (researched, not invented) and a reconciliation precedence rule that never overwrites a newer local terminal state with a stale provider read. **RBAC** — zero new permissions; `billing.view`/`billing.manage`/`subscription.change`/`payment.manage` (all four already frozen in `B1_AUTHORIZATION_RBAC.md`) fully cover B8's surface, including provider-credential management via the existing `payment.manage` scope.
