# B8 — Security Threat Model

> Design only. Threat | Mitigation | Acceptance test | Residual risk, per brief §37.

| # | Threat | Mitigation | Acceptance test | Residual risk |
|---|---|---|---|---|
| T1 | Price tampering (client sends a different `amount`) | `PaymentCreate.amount`/`.currency` are non-authoritative mirrors; server always derives from the stored `UpgradeQuote` (frozen mechanism) | `AT-B8SEC-1`: submit `PaymentCreate` with a mismatched amount; assert `422 QUOTE_MISMATCH`, no Payment created with the tampered value | none — structural |
| T2 | Plan ID tampering (client references a retired/foreign plan) | `CreateUpgradeQuote` validates plan is `active` and resolves under global catalog scope; a nonexistent plan is `404` | `AT-B8SEC-2`: quote a retired plan; assert `422 PLAN_RETIRED` | none |
| T3 | Workspace substitution (IDOR on Subscription/Payment/UpgradeQuote) | workspace-scoped resolution before object lookup (Doctrine R-1/R-2); cross-workspace reference is `404`, indistinguishable from absent | `AT-B8SEC-3`: request another workspace's `SUB-*`/`PAY-*`; assert `404`, and assert response body is byte-identical to a genuinely nonexistent id | none |
| T4 | Provider reference substitution (client supplies a `provider_payment_ref` to claim someone else's charge) | `provider_payment_ref` is never a client-writable field on any B8 request DTO — it is adapter-set only, post-provider-call | `AT-B8SEC-4`: attempt to set `provider_payment_ref` via `PaymentCreate`; assert the field is rejected (`additionalProperties:false`) or silently ignored server-side | none |
| T5 | Fake success redirect | redirect handler never mutates state (§`B8_CHECKOUT_PAYMENT_MODEL.md` §8); only webhook/reconciliation can | `AT-B8SEC-5`: hit the redirect callback with a fabricated `tap_id` claiming success, no matching webhook ever arrives; assert `Subscription`/`Payment` state unchanged | none — structural |
| T6 | Fake webhook (unsigned/forged) | Webhooks-domain signature verification (`hashstring` HMAC-SHA256) gates `verified`; unverified never reaches `ProcessPaymentWebhook` | `AT-B8SEC-6`: POST a forged payload to the Tap webhook route without a valid `hashstring`; assert `401 WEBHOOK_INVALID_SIGNATURE`, zero state mutation | depends on secret-key confidentiality — a leaked Tap secret key defeats this; mitigated by T10 |
| T7 | Replay webhook (valid signature, replayed old event) | dedup identity `(provider, event_id, payload_hash)` at the Webhooks layer; legal-transition check at B8's own consumer layer rejects backward/duplicate application | `AT-B8SEC-7`: replay a previously-processed, validly-signed webhook; assert no duplicate `PaymentSucceeded`, no double subscription activation | none |
| T8 | Duplicate payment (client double-submits checkout) | `Idempotency-Key` + single-consumption `UpgradeQuote` + one-in-flight-payment-per-subscription rule (`B8-D-A012`) | `AT-B8SEC-8`: double-submit `CreatePayment` under the same key; assert one Payment row; under a different key while the first is still pending, assert `409 payment_in_progress` | none |
| T9 | Double upgrade (race to consume the same quote) | frozen quote-consumption transaction + partial unique index on `payment_id` | `AT-B8SEC-9`: fire two concurrent `CreatePayment` against the same `quote_ref`; assert exactly one Payment created, the other `409 CONFLICT` | none |
| T10 | Downgrade/cancel race | row-locked `Subscription`, explicit supersession rules (§`B8_CONCURRENCY_MODEL.md`) | `AT-B8SEC-10`: fire concurrent `ScheduleDowngrade`+`CancelSubscription`; assert deterministic outcome (cancellation wins, downgrade cleared) | none |
| T11 | Privilege escalation (Manager/Sales attempting a billing command) | RBAC step 8 denies before any entitlement/quota exposure | `AT-B8SEC-11`: Sales role calls `CancelSubscription`; assert `403 PERMISSION_DENIED`, no leak of subscription state in the error body | none |
| T12 | Provider secret exposure | secrets in environment/secret management only; `ProviderConfigurationHealth` never returns a value, only booleans/timestamps | `AT-B8SEC-12`: inspect every B8 response schema and log statement for a secret-shaped field; assert none | requires disciplined implementation-time log-statement review; architecture provides no field to leak from |
| T13 | Logs leaking payment/provider data | structured logging omits raw payment payloads/tokens (frozen `BACKEND_OPERATIONS_OBSERVABILITY.md`); B8 logs only `Payment.public_id`/`status`/amount-as-decimal, never provider raw JSON | `AT-B8SEC-13`: trigger a full payment flow in a test environment; grep logs for card-shaped or raw-provider-payload content; assert none | log-statement discipline is implementation-time, not architecture-enforceable beyond the retention/classification rule (§`B8_PRIVACY_RETENTION.md`) |
| T14 | Cross-tenant billing read | identical to T3 — workspace-scoped resolution | covered by `AT-B8SEC-3` | none |
| T15 | Admin override abuse / privilege escalation (a member without `billing.manage` grants themselves an entitlement override, or a `billing.manage` holder uses it beyond audited broadening) | RBAC gates `GrantEntitlementOverride`/`RevokeEntitlementOverride` on `billing.manage` (denied for Manager/Sales/Member/Viewer, §`B8_RBAC_TENANCY.md` §2); overrides are audited (`EntitlementOverrideGranted`, `AUD-*`), broaden-only (`B8-D-A014`), and require `reason` (non-empty, required field on `EntitlementOverrideCreate`) | `AT-B8SEC-15`: grant an override; assert an audit row with actor, reason, and expiry is created and queryable. `AT-B8RBAC-1`…`4`: non-`billing.manage` roles denied `403 PERMISSION_DENIED` | relies on org-level oversight of who holds `billing.manage`; architecture provides full auditability but not organizational policy |
| T20 | Override stacking (an admin or a race attempting to compound two overrides on the same `(workspace, code)` into an unbounded effective grant) | structurally impossible, not merely discouraged: the partial unique index `(workspace_id, code) WHERE status='active'` (`B8-D-A021`) guarantees at most one active override row exists at any time, and its stored value is applied through a single `MAX` against the current base (`B8-D-A022`), never an additive sum across rows — there is never more than one override value to compound | `AT-B8OVR-4` (concurrent first-grant race → exactly one active row), `AT-B8OVR-5` (replacement leaves exactly one active row), `AT-B8OVR-10` (metered override is `MAX`, not addition) | none — structural |
| T21 | Cross-tenant override collision (an override granted in one workspace bleeding into, or colliding with, another workspace's resolution of the same capability/metric code) | `entitlement_overrides` is workspace-scoped (`workspace_id` column, part of both the partial unique index and every lookup predicate, §`B8_STORAGE_MODEL.md`); resolution always filters by the requesting workspace's own `workspace_id` (identical mechanism to T3/T14's workspace-scoped resolution) | `AT-B8OVR-8`: an active override for `code=X` in workspace A does not affect, and is not visible to, workspace B's resolution of the same `code=X` | none — identical to T3's structural guarantee |
| T16 | Trial abuse (repeated trial via re-created workspace) | `trial_used_at` is workspace-scoped, not user-scoped; repeated-workspace-creation abuse is a Workspace/B1-domain concern (rate-limited account/workspace creation), out of B8's own scope | `AT-B8SEC-16` (mechanism-only, since trials are inactive): assert a workspace with `trial_used_at` set cannot `StartTrial` again | acknowledged residual: multi-workspace trial abuse via account creation is a B1-domain mitigation, not eliminated by B8 alone; recorded as `B8-D-C007` |
| T17 | Quota bypass (direct write to `usage_counters` bypassing reservation) | `usage_counters` writes only happen inside the reserving domain's own transaction, behind `SELECT...FOR UPDATE`; no client-facing endpoint writes it directly | `AT-B8SEC-17`: attempt to call any B8 endpoint with a body field targeting `usage_counters.count`; assert no such field exists on any request DTO | none |
| T18 | Entitlement cache staleness | no server-side entitlement caching exists in Phase 1 (§`B8_ENTITLEMENT_MODEL.md` §7) | `AT-B8SEC-18`: change plan, immediately re-query `GET /entitlements`; assert the new grant is reflected with zero propagation delay | none in Phase 1; becomes a live risk only if `B8-D-C006` (future caching) is later adopted, at which point its own invalidation proof is required before shipping |
| T19 | Provider/local disagreement exploited to claim unpaid access | reconciliation `RECONCILIATION_MISMATCH` never auto-resolves in the client's favor; ambiguous states default to `pending` (fail-closed, §`B8_PAYMENT_PROVIDER_PORT.md` §3) | `AT-B8SEC-19`: force an unrecognized Tap status; assert `Payment` stays `pending`, no entitlement granted | none |

`AT-B8SEC-*` full definitions and pass/fail evidence live in `B8_ACCEPTANCE_TESTS.md`.
