## `entitlement_overrides` persistence pattern (`B8-D-A021`)

The uniqueness invariant — at most one effective override per `(workspace_id, code)` — is enforced by a **status column**, never by a time comparison inside an index predicate. `status` is an ordinary, transactionally-updated enum column (`active` | `revoked` | `expired`); the partial unique index `(workspace_id, code) WHERE status = 'active'` is a valid, immutable PostgreSQL predicate because it depends only on stored column values, never on `now()` or any other volatile function — a `now()`-based partial-index predicate would be rejected by PostgreSQL outright (index predicates must be immutable) and is explicitly not used here. Time-based expiry (`expires_at`) is a **read-time filter** applied by the entitlement-resolution algorithm (`B8_ENTITLEMENT_MODEL.md` §5) on top of the structurally-guaranteed single `active` row, never a second source of uniqueness truth. A row's `status` transitions `active → expired` only through the reconciliation sweep's own write (best-effort, for read-model/audit accuracy) or lazily on next write-touch — never required for the resolution algorithm's own correctness, which independently treats a past-`expires_at` `active` row as inapplicable at read time regardless of whether the sweep has run.

## `entitlement_overrides` lifecycle (`B8-D-A021`)

| Transition | Command | Actor | Preconditions | Mechanics |
|---|---|---|---|---|
| *(none)* → `active` (first grant for a code) | `GrantEntitlementOverride` | admin (`billing.manage`) | no existing `active` row for `(workspace_id, code)`; passes creation-time validation (`B8_ENTITLEMENT_MODEL.md` §5c) | single-row `INSERT`; partial unique index is the transactional backstop against a concurrent racing insert |
| `active` (old) → `revoked`, *(none)* → `active` (new) — replacement/re-grant | `GrantEntitlementOverride` | admin (`billing.manage`) | an `active` row already exists for `(workspace_id, code)` | one transaction: `SELECT ... FOR UPDATE` the existing active row, set it `revoked` (`revoked_at = now()`, `revoked_by_membership_id = actor`, `reason` annotated "superseded by re-grant"), then `INSERT` the new `active` row — the old row is never deleted, only closed |
| `active` → `revoked` | `RevokeEntitlementOverride` | admin (`billing.manage`) | row is currently `active` | sets `revoked_at`/`revoked_by_membership_id`; idempotent replay under the same `Idempotency-Key` returns the same result; a genuinely new request against an already-non-`active` row returns `409 CONFLICT` (reason `override_not_active`) |
| `active` → `expired` | reconciliation sweep (system) | n/a | `expires_at IS NOT NULL AND expires_at <= now()` | best-effort, audit/read-model accuracy only — never load-bearing for resolution correctness (§ pattern above) |

Concurrency: two simultaneous `GrantEntitlementOverride` calls for the same `(workspace_id, code)` are serialized by the `SELECT ... FOR UPDATE` on any existing active row; if no row exists yet for either transaction to lock (both racing to create the *first* grant), the partial unique index is the backstop — the losing transaction's `INSERT` fails the unique constraint and is mapped to `409 CONFLICT` (reason `override_already_active`), safe for the client to retry as a replacement grant. Idempotency (`Idempotency-Key`) prevents a client-side retry of the *same* request from being misinterpreted as a second, independent grant attempt.

## JSONB usage

Zero JSONB columns are introduced by B8 for core relationships, state, or ownership, consistent with `BACKEND_DATA_GOVERNANCE.md`'s "JSONB is allowed only for provider metadata, raw snapshots... not for core relationships, state, or ownership." The one bounded, justified JSONB candidate — a short-lived normalized-webhook-event snapshot — belongs to the shared `webhook_receipts` table, which B8 does not own (§`B8_WEBHOOK_MODEL.md` §1); B8 itself defines no JSONB column on any table above. "Provider payload dumping is prohibited," per brief §46 — every B8 table stores only typed, named columns.

## Money representation

Every monetary column above (`plan_versions.price`, `upgrade_quotes.amount`, `payments.amount`, `refunds.amount`, `invoices.total`, `invoice_lines.amount`) is `NUMERIC(19,4)` plus a paired ISO-4217 `currency CHAR(3)` column — never float, per ADR-011, applied uniformly with zero exceptions.
