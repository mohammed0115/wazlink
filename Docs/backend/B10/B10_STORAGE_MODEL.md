## `legal_sequence_number` allocation (`B10-D-A017`)

A per-`(legal_entity_id, environment)` monotonic sequence, allocated transactionally at the moment `IssueTaxInvoice` assigns it (only under `applicable_not_enabled`/`enabled`/`suspended`), backed by a DB sequence or an equivalent serializable-allocation pattern — never a client-suppliable value, never reused after a cancellation (a cancelled document's number is retired, not recycled, consistent with the general "documents are append-only evidence" doctrine `BACKEND_DATA_MODEL.md` establishes elsewhere in the corpus).

## `tax_profiles` versioning pattern

Identical in shape to `B8_PLAN_CATALOG.md` §5's `PlanVersion` pattern: at most one row per `legal_entity_id` has `effective_to IS NULL`; publishing a new profile (via `UpdateTaxProfile`/`SetTaxApplicability`) closes the prior row's `effective_to` and inserts the new row in the same transaction.

## `pending_tax_document_classifications` — durable model for the `unknown`-mode backlog (`B10-FIX.1`, closes `B10-AUDIT-M2`)

Full field list, states, idempotency, and resolution semantics: §`B10_TAX_APPLICABILITY_MODEL.md` §3 (updated), §`B10_IDEMPOTENCY_CONCURRENCY.md` §5 (new), §`B10_COMMAND_EVENT_CATALOG.md` §1 (`ResolvePendingTaxClassification`, new). Summary: created by `IssueTaxInvoice` itself (not a separate trigger) the moment it observes `TaxProfile.zatca_applicability = unknown` for a newly-consumed `InvoiceIssued` event, in place of the pre-FIX.1 pack's undocumented "no row created yet" behavior. Resolved by the new `ResolvePendingTaxClassification` command, invoked by a scheduled sweep after every `TaxApplicabilityChanged` event and additionally operator-invokable (mirroring `RetryTaxSubmission`'s dual system/operator invocation shape). Resolution never duplicates a `TaxInvoice`: when the outcome is issuance, `ResolvePendingTaxClassification` calls the existing `IssueTaxInvoice` command for the same `source_ref`, which is already idempotent on `(source_type, source_ref)` via `tax_invoices`' own partial unique index.

## JSONB usage

Zero JSONB columns are introduced by B10 for core relationships, state, or ownership, consistent with `BACKEND_DATA_GOVERNANCE.md`'s restriction (identical discipline to `B8_STORAGE_MODEL.md`'s "JSONB usage" section) — address fields, seller/buyer snapshots, and every other structured value are typed, named columns.

## Money representation (rounding rule corrected under `B10-FIX.1`)

Every monetary column above is `NUMERIC(19,4)` plus a paired ISO-4217 `currency CHAR(3)` column — never float. `tax_invoices.tax_amount` is **not** a row-level-checkable sum of `tax_invoice_lines.tax_amount` (the pre-FIX.1 assumption, now corrected); it is computed at the VAT-category-subtotal level and written atomically alongside the lines in the same `IssueTaxInvoice` transaction — an application-layer invariant, not a DB `CHECK`, for the same reason `B10_CREDIT_NOTE_MODEL.md`'s cross-table reference-type check is application-layer: it aggregates across sibling rows grouped by a computed key (`tax_category`, `tax_rate`), which a single-row `CHECK` cannot express. Full algorithm: `B10_CURRENCY_MONEY_ROUNDING.md`.
