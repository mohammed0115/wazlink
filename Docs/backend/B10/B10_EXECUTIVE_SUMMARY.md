## What B10 found before designing anything

Unlike most prior phases, B10 inherits almost nothing pre-built: frozen B0 named the `Tax` domain, the `TaxInvoice` aggregate, the `tax_invoices`/`lines`/`submissions` table group, the `TAX-*` prefix, the `SubmitTaxInvoice`/`TaxSubmitted` command/event names, the `TaxProvider` integration port, and a `tax.view` permission — but left every field, state, and rule marked `REQUIRES OFFICIAL ZATCA VALIDATION` (ADR-012). B9, freshly closed, independently pre-committed a symmetric boundary (`B9_B10_TAX_BOUNDARY.md`) declaring exactly what B10 may ever read from Finance and what it must never infer. B10's task was to fill this entire skeleton in, from real research, without inventing a single legal claim.

## The central design problem, and its resolution

The product owner has stated the current WazLink operating entity is exempt from ZATCA's e-invoicing requirement. Treating that as settled architecture would have been wrong twice over: it would hard-code an unverified legal claim, and it would make the platform unable to represent "we don't yet know" or "we're obligated but not yet integrated" — both real, common states. B10 instead defines a **five-state `zatca_applicability` model** (`unknown | not_applicable | applicable_not_enabled | enabled | suspended`, `B10-D-A002`) attached to a new, **platform-scoped** `LegalEntity`/`TaxProfile` aggregate (`B10-D-A001` — deliberately not workspace-scoped, because applicability is a property of WazLink as seller, not of any individual buyer workspace). The current target deployment configures this as `unknown` at bootstrap, moving to `not_applicable` only through an explicit, Owner-only, audited, reason-required admin action (`B10-D-A016`) — never asserted by this document pack itself. See `B10-X-OWNER-EXEMPTION` (`B10_RESEARCH_REGISTER.md` §2) for the precise, honest framing of that business-supplied claim.

## What B10 designed

**Legal Entity & Tax Profile** — a versioned, snapshot-safe configuration aggregate (`B10_LEGAL_ENTITY_TAX_PROFILE.md`) that a future applicability change never retroactively rewrites (`B10-D-A008`). **Invoice/Note model** — `TaxInvoice` hosts every document shape via **two independent columns, corrected under `B10-FIX.1`**: `document_kind` (invoice/credit/debit — the economic direction) and `invoice_classification` (standard/simplified — the sole determinant of ZATCA routing, inherited immutably by notes from the invoice they correct), requiring zero new tables and zero new public-ID prefix beyond the already-frozen `TAX-*` (`B10-D-A004`). **ZATCA clearance/reporting routing** — corrected under `B10-FIX.1`: routed solely by `invoice_classification`, never by credit-vs-debit note type, closing a CRITICAL finding from independent audit (`B10-AUDIT-C1`). **Tax rounding** — corrected under `B10-FIX.1`: VAT is rounded once per tax-category subtotal and the document total is the sum of already-rounded category amounts, matching the official ZATCA XML Implementation Standard's document-level rule (the original pass had this backwards). **Unknown-mode backlog** — corrected under `B10-FIX.1`: a durable `PendingTaxDocumentClassification` aggregate with explicit states, idempotent creation, and a dedicated resolution command, replacing the original pass's prose-only description. **Tax calculation** — a four-category rate model (standard/zero-rated/exempt/out-of-scope) that computes nothing at all while the current deployment stays `not_applicable`, but is fully specified for the moment it doesn't. **ZATCA phase mapping** — real, researched Phase 1 (Generation, since Dec 2021) vs. Phase 2 (Integration, waves since 2023) semantics mapped directly onto the applicability states (`B10-D-A018`), so `applicable_not_enabled` is architecturally the correct representation of a taxpayer who must generate-and-store but isn't yet integrated — not an error state. **Legal numbering** — corrected under `B10-FIX.1`: `legal_sequence_number` is recorded as a WazLink product/legal sequence, explicitly not asserted to be ZATCA's device/EGS-unit-scoped Invoice Counter Value. **Cumulative correction consistency** — new under `B10-FIX.1`: a row-locked `net_corrected_total ≥ 0` invariant bounds credit/debit notes against their original, as a WazLink product rule rather than an invented statutory one. **Credentials** — CSID/certificate material is an opaque secret-store pointer only, never a database plaintext value, mirroring B8's Tap-credential discipline exactly. **B8/B9 boundaries** — three explicit non-identities held from B10's own side, symmetric to what B9 already committed to from its side: `Refund ≠ CreditNote`, `CreditNote ≠ RevenueReversal`, `Invoice (B8) ≠ TaxInvoice (B10)`.

## Firewalls, restated a domain further

> **PAYMENT SUCCESS ≠ TAX OBLIGATION ≠ RECOGNIZED REVENUE.** B10 has zero write path to `revenue_events`/`revenue_reversals`/`attribution_touchpoints` (unchanged from B9's own firewall) and zero write path to any B8-owned table. A B8 `Refund` never automatically creates a B10 `CreditNote`; a B10 `CreditNote` never automatically creates a B9 `RevenueReversal`. Full proof: `B10_B8_BILLING_BOUNDARY.md`, `B10_B9_FINANCE_BOUNDARY.md`.

## Research, not invention

Sixteen external ZATCA facts are now recorded (`B10-FIX.1` adds three: note-classification routing, EGS-unit/ICV scoping, and the corrected rounding rule) — 2 `VERIFIED` directly from `zatca.gov.sa` (unchanged; no fact is promoted to `VERIFIED` from secondary sources alone, per explicit instruction), 10 `PARTIAL` (corroborated by multiple concordant secondary sources — several of the `B10-FIX.1` additions notably strengthened by sources citing exact EN16931/UNCL1001 technical identifiers, though still not primary-source-confirmed since the official XML Implementation Standard PDF could not be rendered to readable text by any tool available in this environment), 3 `UNRESOLVED` (exact QR/XML/cryptographic-stamp technical encoding, unchanged), and 1 `CONTRADICTED` (the original per-line rounding proposition, superseded by the corrected document-level rule). Zero item is invented. None of the three `UNRESOLVED` items blocks Phase-1 architecture, because the current target deployment never reaches the `enabled` path that would need them. See `B10_RESEARCH_REGISTER.md`.
