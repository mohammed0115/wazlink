# B4 — Failure Scenario Catalog

> **B4 status:** Target design only. Each scenario names a deterministic outcome and the document that governs it — no scenario is left as "TBD."

| # | Scenario | Expected deterministic behavior | Governed by |
|---|---|---|---|
| DF1 | Business deleted/archived during analysis | run completes/fails/cancels normally; result retained but excluded from new admission going forward (Business no longer resolvable in workspace scope for *new* requests) | `B4_IDEMPOTENCY_CONCURRENCY.md` §7 |
| DF2 | Business rediscovered during analysis | in-flight run unaffected; `businesses.version` bump only affects *future* reads' staleness computation, never the in-flight run's own snapshot | `B4_FRESHNESS_STALENESS.md` §6 |
| DF3 | Two concurrent `RequestBusinessIntelligence` for the same Business, same input | both admit or coalesce onto one run via the `(business_id, input_hash)` reuse check; never two runs for identical input | `B4_COST_RATE_LIMIT_MODEL.md` §7, `B4_IDEMPOTENCY_CONCURRENCY.md` §3 |
| DF4 | Duplicate `Idempotency-Key` | stored response replayed; no second admission, no second slot | `B4_COST_RATE_LIMIT_MODEL.md` §8 |
| DF5 | Same input already analyzed (non-stale, completed) | reused, not re-admitted — `outcome=reused` in `IntelligenceAdmissionResult` | `B4_COST_RATE_LIMIT_MODEL.md` §7 |
| DF6 | Provider timeout | automatic retry ≤3, then `failed` if the timed-out call was required, `partial` if optional | `B4_RETRY_FAILURE_MODEL.md` §2–§3 |
| DF7 | Provider rate limit (429) | automatic retry honoring `Retry-After`, ≤3, same terminal rule as DF6 | `B4_RETRY_FAILURE_MODEL.md` §2 |
| DF8 | Malformed JSON from provider | `schema_invalid`, no repair attempt, retried as a fresh attempt up to ≤3 | `B4_PROVIDER_STRUCTURED_OUTPUT_CONTRACT.md` §4 |
| DF9 | Valid JSON, invalid enum value | `schema_invalid` — value not coerced to nearest match | `B4_PROVIDER_STRUCTURED_OUTPUT_CONTRACT.md` §4 |
| DF10 | Provider response cites an evidence reference not in the supplied set | `schema_invalid` — fabricated reference, rejected outright | `B4_PROVIDER_STRUCTURED_OUTPUT_CONTRACT.md` §4, `B4_RECOMMENDATION_MODEL.md` §5 |
| DF11 | Provider output contains an unsupported (evidence-free) claim | rejected at validation; the claim never reaches a `Signal`/`Recommendation`/artifact field | `B4_EVIDENCE_MODEL.md` §1, `B4_RECOMMENDATION_MODEL.md` §5 |
| DF12 | Input payload too large for provider limits | rejected before send — `B4_INPUT_SNAPSHOT_MODEL.md` §2's minimized payload is bounded by construction (a Business's normalized fields are already small); if a future field addition risks this, the size cap is a Class B admission check, not a runtime surprise | `B4_INPUT_SNAPSHOT_MODEL.md` §2 |
| DF13 | Provider output too large (exceeds `max_output_tokens`) | provider truncation is treated as `schema_invalid` (an incomplete structured response fails schema validation) — never silently accepted truncated | `B4_PROVIDER_STRUCTURED_OUTPUT_CONTRACT.md` §2, §4 |
| DF14 | Provider safety refusal | Class B component → `failed`; Class C component → `partial`, per the required/optional split | `B4_RETRY_FAILURE_MODEL.md` §2–§3 |
| DF15 | Analysis succeeds locally but the completion DB commit fails | run is quarantined, `internal_error`; the prior `completed` run (if any) remains current — no half-written run ever becomes visible | `B4_INTELLIGENCE_RUN_STATE_MACHINE.md` §4, `B4_RETRY_FAILURE_MODEL.md` §2 |
| DF16 | An older run completes after a newer run already went current | older run retained as history, never overwrites `is_current` | `B4_IDEMPOTENCY_CONCURRENCY.md` §4–§5 |
| DF17 | `scoring_model_version` changes mid-run | the run completes under the version it started with (`scoring_model_version` fixed at admission, not re-read mid-run); a newer-versioned run, once it exists and completes, is what future reads see as current | `B4_SCORING_MODEL.md` §8 |
| DF18 | Recommendation would be based on stale evidence | `B4_RECOMMENDATION_MODEL.md` only ever derives from the run's own (fixed) snapshot; staleness is a property of the *whole run* relative to *current* Business state, surfaced at read time, never silently baked into a new recommendation without a fresh run | `B4_FRESHNESS_STALENESS.md` §3 |
| DF19 | Low evidence but a provider call returns high confidence anyway | provider-reported confidence (if any) is never trusted directly — B4's own confidence model (`B4_SCORING_MODEL.md` §7) is computed independently from evidence quantity/quality/agreement, overriding any confidence value a provider response might include |
| DF20 | Cross-workspace cache collision attempt | structurally prevented — every reuse/cache key is `(workspace_id, business_id, input_hash)` | `B4_AUTHORIZATION_TENANCY.md` §7 |
| DF21 | User spams re-analysis (rapid repeated `ReanalyzeBusinessIntelligence`) | bounded by the shared 60/hour workspace admission counter (`B4-D-A017`) — the 61st request in the rolling hour is `429`, regardless of how many distinct Businesses or how rapid | `B4_COST_RATE_LIMIT_MODEL.md` §2, §6 |
| DF22 | Automatic trigger storm from rediscovery | impossible by construction — there is no automatic trigger in Phase 1 (`B4-D-C001`) | `B4_FRESHNESS_STALENESS.md` §5 |
| DF23 | Cancellation requested after the provider call has already started | cooperative cancellation checked only before the call and after structured-output validation, never mid-call — the in-flight call is allowed to finish so its cost is not wasted and its evidence not discarded; the run then transitions to `cancelled` at the next checkpoint | `B4_INTELLIGENCE_RUN_STATE_MACHINE.md` §5 |
| DF24 | Partial deterministic success / AI (Class C) failure | run `completed`, `completion_kind=partial`, score/signals/recommendations fully valid, `presentation=null` | `B4_RETRY_FAILURE_MODEL.md` §3 |
| DF25 | AI-generated summary disagrees with a structured signal | cannot occur by construction — the presentation artifact is generated *after* signals/recommendations are finalized and is validated to cite only their `evidence_ref`s (`B4_RECOMMENDATION_MODEL.md` §6); a provider response attempting to introduce a contradicting claim fails schema validation (DF11) |
| DF26 | Provider response contains unexpected/secret-looking data | never persisted — only fields matching the closed schema are extracted; anything else is discarded at the validation boundary, and the raw response itself is never stored (`B4_PROVIDER_STRUCTURED_OUTPUT_CONTRACT.md` §8) |
| DF27 | Business converts to Lead mid-run | no effect on the run; `Lead360.intelligence` starts resolving through the new Lead once the run completes, same as any other completed run | `B4_IDEMPOTENCY_CONCURRENCY.md` §6, `B4_B2_CRM_LEAD360_BOUNDARY.md` §3 |
| DF28 | Archived Lead still points to Business intelligence | continues to resolve live via `lead.business_id`, subject only to B2's own archived-Lead read rules, not any B4-imposed restriction | `B4_B2_CRM_LEAD360_BOUNDARY.md` §5 |
| DF29 | Deleted/expired evidence source (e.g. the Discovery observation an evidence item pointed to is later corrected by a subsequent rediscovery) | the historical `Evidence.extracted_value` on a completed run is immutable and unaffected — it reflects what was true *at that run's snapshot time*; only a *new* run reflects the corrected value | `B4_EVIDENCE_MODEL.md` §2, `B4_INTELLIGENCE_RUN_STATE_MACHINE.md` §2 |
| DF30 | Score becomes stale while a Lead 360 view is already open | the open view shows what it fetched; the next `GET` (e.g. on refresh, or the summary endpoint's next poll) computes `stale: true` fresh — no push/invalidation mechanism is required or assumed | `B4_FRESHNESS_STALENESS.md` §2 |
| DF31 | Batch request names more than 20 Business IDs | rejected in full before any admission — `422`, `batch_size_exceeded` | `B4_COST_RATE_LIMIT_MODEL.md` §3 |
| DF32 | Batch request partially exhausts the hourly counter mid-batch | admitted per-ID until the counter is exhausted, remainder individually `429` in the same `202` response | `B4_COST_RATE_LIMIT_MODEL.md` §4 |
| DF33 | `AnalyzeLead` called for a Lead whose Business was merged away (tombstoned) | resolves through the tombstone to the surviving Business, exactly as B3's own merge-aware resolution requires elsewhere in this corpus | `B4_B3_ACQUISITION_BOUNDARY.md` §4 |
| DF34 | A recommendation is requested from an `insufficient_data` run | never produced — `insufficient_data` runs yield zero recommendations by construction | `B4_SCORING_MODEL.md` §6, `B4_RECOMMENDATION_MODEL.md` §4 |
| DF35 | Actor without `intelligence.run` attempts to trigger analysis via the `AnalyzeLead` alias | `403 PERMISSION_DENIED` — the alias delegates to the identical permission check as the primary command, not a weaker one | `B4_INTELLIGENCE_SUBJECT_MODEL.md` §4, `B4_AUTHORIZATION_TENANCY.md` §2 |

`FAILURE_SCENARIO_COUNT = 35` (DF1–DF35, contiguous).
