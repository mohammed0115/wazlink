# B12 — Provider Research Register

> Design only. Every material external claim in this pack is cited here. `STATUS` is exactly one of `VERIFIED` (read directly from the provider's or standards body's own documentation during this authoring pass), `PARTIAL` (established by an authoritative-but-secondary source, or read primarily but incompletely), `UNRESOLVED` (no readable source established the fact during this pass), or `CONTRADICTED`. No claim is promoted to `VERIFIED` on the strength of a secondary source.

## 2. On the ratings

Nine facts are `VERIFIED` and every one was fetched from the provider's own documentation during this pass — Meta's Graph API webhooks guide, Tap's webhook page, and Google's Places usage-and-billing page. One is `PARTIAL`: `B12-X-014`'s raw-byte basis is asserted by frozen B5 and is **safe under either reading**, so the design does not turn on it. Five are `UNRESOLVED`, four of them the same question — *does this provider offer an idempotency key?* — and the answer being unknown for all four is precisely why `B12-D-A012` refuses to depend on one.

**No unresolved item blocks Phase-1 architecture.** Each gates an optimization (`011`, `012`, `013`), is irrelevant to a read-only API (`010`), or belongs to a frozen phase that already declared it non-blocking (`015`). `CLASS_A_UNRESOLVED = 0` follows from this, not from optimism.

## 3. Claims B12 explicitly does NOT make

- That any Phase-1 provider supports a client-supplied idempotency key.
- That any provider's signature scheme includes timestamp/nonce replay protection (Tap's `x_created` is *inside* the signed set but its freshness semantics were not established).
- That Meta documents a raw-byte signature basis.
- That any provider publishes stable IP ranges suitable for an allow-list.
- That Tap will retry a callback more than three times in total.
- That WhatsApp status callbacks arrive in order.
- That any provider offers webhook replay on demand.
- That credentials are encrypted at rest by the deployed target.
- That any compliance, PCI, or data-locality property holds.

## 4. Re-verification gate

Every `VERIFIED` fact is a **snapshot of documentation on the date of this pass**, not a permanent truth. `B12_IMPLEMENTATION_HANDOFF.md` §1 makes re-verification of `B12-X-001`, `005`, `006`, and `014` a pre-implementation gate, because a change to a signature scheme or a retry bound would invalidate a load-bearing control rather than merely a comment.
