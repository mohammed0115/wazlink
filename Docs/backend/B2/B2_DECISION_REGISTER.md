| `B2-D-A025` | What is a timeline entry's identity, its total order, and its cursor? | **`entry_id` is an immutable globally-unique text token in one of two structurally disjoint shapes:** `ACT-*` for CRM-owned entries, `<source_domain>:<source_event_id>` for cross-domain entries. One logical event yields exactly one entry. **No new public-ID namespace is minted.** Disjointness of the two shapes follows from the registry's **case-sensitive registered uppercase prefixes** versus the lowercase `source_domain` token — not from any character-set grammar, which the registry does not define | using `DEAL-4042` as an entry identity collapses four Deal events into one entry; deriving an identity from an aggregate `version` is not replay-stable; and ordering on a mutable scheduling field lets a reschedule silently relocate history and invalidate every issued cursor | timeline, cursor, dedup | AT-TL-2, AT-TL-8, AT-TL-ID-1…11, AT-TL-ORDER-1…3 |
| `B2-D-A026` | How are future-dated cross-domain timestamps handled? | **Bounded-skew eligibility, evaluated at two points, with no rewriting.** One source-independent constant `CLOCK_SKEW_TOLERANCE` (default 300s) and one comparison `skew = occurred_at − reference_time`. **Timeline (read path):** a record with `skew > tolerance` is not eligible to become a `TimelineEntry` — no entry, no placeholder, no cursor position. The filter is re-evaluated on every read, so it **self-heals**: the record appears exactly once, with the same `entry_id`, on the first read where it is valid. **Persisting consumers:** the same check runs against a `processing_reference_time` **sampled afresh at the start of every processing attempt** (§5.2.1) — never a first-receipt stamp, an ingestion instant, an immutable `ingested_at`, or a cached value. This is **one clock model for every consumer that persists on the strength of a source timestamp**, not a `last_activity_at` special case: it binds the `last_activity_at` consumer (a rejected event does not advance the monotonic column) and, identically, the `RecordLeadRediscoveryProvenance` consumer of `B2_REDISCOVERY_PROVENANCE_PROCESS.md` §2.5, which delegates to §5.2.1 and defines no clock of its own (generalized at **B2-FIX.4.1**; a defect-scope correction, not a new decision). **How a rejected event is subsequently recovered is not part of this decision** — it is closed separately by `B2-D-A027`, which replaces the earlier and unsound "re-evaluated only on source redelivery". Past-dated records are always eligible, and **eligibility is never decided once and cached** — it is recomputed on every read and on every processing attempt. `occurred_at` is never clamped or rewritten, and **no CRM quarantine store exists** — an operational alert is monitoring only, and no behavior is conditioned on it | `GREATEST()` makes `last_activity_at` monotonic, so a single event stamped in 2099 poisons it permanently; clamping would mutate a field the total order and every issued cursor treat as immutable, and would not be replay-stable. A consumer-only gate could not work at all, because cross-domain entries are read from owning-domain records at query time and never pass through a CRM consumer | `last_activity_at`, timeline ordering, consumed events, rediscovery provenance | AT-TL-SKEW-1…5, AT-DUP-5J |
| `B2-D-A027` | After a future-clock-skew rejection, what guarantees that `last_activity_at` ever recovers? | **A future-skew rejection is a `RETRYABLE_CLOCK_SKEW` processing failure, never a processed event.** The consumer must not acknowledge successful completion while the event is outside tolerance. Every delivery resolves to exactly one of three states — `ELIGIBLE` (apply `GREATEST()`, then ack after commit), `RETRY_PENDING` (not acknowledged as successful; re-delivered under a **bounded** policy: finite attempts and/or finite retry age, increasing backoff, stable event identity, at most one effect on `last_activity_at`), `DEAD_LETTERED` (budget exhausted: durable, alerted, operator-visible, retaining the original `event_id`, `reason = CLOCK_SKEW`, `workspace_id`, source/aggregate references and an unclamped `occurred_at`). **Eligibility is re-evaluated on every attempt against a `processing_reference_time` sampled afresh when that attempt begins** (§5.2.1) — never a first-receipt or cached clock — which is what makes automatic recovery reachable at all. Recovery is by **automatic bounded retry** once the trusted clock reaches eligibility, or by **operational replay** from `DEAD_LETTERED`; either way the original event is re-evaluated against the same §5.2 rule, keeps the same `event_id`/`source_event_id`, synthesizes no new business event, creates no timeline entry, and is idempotent. **No permanent under-count may arise solely from a future-skewed first delivery.** A recovered event is passed through `GREATEST()` like any other eligible qualifying event and is **never discarded** for having a lower aggregate version, an older delivery position, or a later arrival than events already applied from the same aggregate. The bound binds to frozen B0 `BACKEND_RETRY_POLICY.md`; concrete numbers stay operational configuration, and the queue, scheduler, dead-letter store and replay tooling belong to **B12 — Async & Integration Platform**, which B2 depends on and does not design. **No CRM quarantine aggregate, table, column, or DTO field is introduced** | at-least-once delivery guarantees redelivery only until a message is acknowledged, and nothing after. The prior contract said a rejection "stands until the source redelivers the event" — but nothing made the source redeliver an event the consumer had already acked, so `last_activity_at`, an `AUTHORITATIVE_PERSISTED` column driving list sort and stale-lead UX, could stay permanently stale. Recovery of persisted state must be *caused* by the consumer refusing to ack, not *assumed* from the transport. Stating one disposition also stops an implementation agent choosing between ack-and-drop, an infinite NACK loop, a bounded retry, and a silent ignore | `last_activity_at`, consumed events, async-platform dependency | AT-TL-SKEW-6…10 |

## 5. Closure statement

No Class B or Class C item prevents the B2 architecture from being closed and handed to an implementation agent. Each Class B item has a decided target and needs only a controlled edit; each Class C item has a stated Phase-1 default or an explicit `NOT_SUPPORTED`, so implementation proceeds deterministically and the decision can later be applied without re-architecture.

**One gate stands before implementation:** the controlled amendment bundle in `B2_CONTROLLED_AMENDMENTS.md` must be approved and applied. Until then no implementation may mint `NOTE-*`, enforce `lead.archive`, ship any of the 25 additive operations, or rely on the amended `Lead360` shape.
