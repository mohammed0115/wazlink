# B11 — Decision Register

> `CLASS_A_UNRESOLVED = 0`. Every Class A decision below has an enforcement artifact and acceptance evidence. Two competent engineers reading this register plus the documents it cites should derive identical behavior without inventing a rule.

## Class A — must be resolved before implementation

| ID | Question | Decision | Reason | Enforcement artifact | Acceptance evidence |
|---|---|---|---|---|---|
| `B11-D-A001` | What is a File in WazLink? | A **`FileAsset`**: a workspace-scoped PostgreSQL row naming exactly one immutable blob-storage object. **The row is the file; the bytes are not.** A row with no bytes is a legitimate state (`pending`); bytes with no row are an anomaly | Every later rule — tenancy, integrity, deletion, reconciliation — needs one unambiguous answer to "what is being authorized." Making the bytes the file would leave "authorized by whom" answerable only by asking the provider | `B11_DOMAIN_MODEL.md` §1 | `AT-B11UP-1`, `AT-B11REC-1` |
| `B11-D-A002` | Who owns file metadata? | B11 exclusively, in `file_assets` (frozen table). No other domain writes it; B11 writes no other domain's table | Frozen `BACKEND_DOMAIN_OWNERSHIP.md` already assigns it, and `B5_DATA_MODEL.md` line 12 already declares B5 has no write credential to `file_assets` | `B11_SCOPE_AND_OWNERSHIP.md` §2 | `AT-B11MSG-1`, `AT-B11TAX-1`, `AT-B11B8-1`, `AT-B11B9-1` |
| `B11-D-A003` | Where do bytes live, and can a URL ever be identity? | Bytes live in blob storage addressed by `storage_key`. **No URL is ever identity** — not a column, not a DTO field, not an event payload, not a log line. `FileDownload.download_url` is always an application URL, never a provider one | Frozen §5's "never use a public URL as the durable identity"; a provider URL changes when a provider changes, so identity built on one is identity that expires | `B11_DOMAIN_MODEL.md` §1, `B11_API_DTO_CONTRACTS.md` §2 | `AT-B11DL-1`, `AT-B11SEC-3`, `AT-B11UP-6` |
| `B11-D-A004` | Is a new public-ID prefix required? | **No.** `FILE-` is already registered in frozen `BACKEND_PUBLIC_ID_REGISTRY.md` section A for `FileAsset` in the Files domain, workspace-scoped. Reused verbatim for every state, type, retention class, and subject. Three candidate prefixes were considered and rejected | The brief warns against assuming a prefix is needed; three separate reviews of the frozen registry found `FILE-` already covers every identity B11 mints | `B11_PUBLIC_ID_REGISTRY.md` | `AT-B11MSG-4` |
| `B11-D-A005` | How is tenant isolation enforced? | By **application authorization only** — frozen Doctrine R-1/R-2. `workspace_id` is NOT NULL; a foreign `FILE-*` is `404`. The `w/<workspace_uuid>/` key prefix is defence in depth and is **never parsed for an access decision** | Relying on path naming moves an authorization decision into string parsing, breaks silently when a key format changes, and gives no answer at all for an object whose row is missing | `B11_RBAC_TENANCY.md` §3, `B11_STORAGE_KEY_MODEL.md` §4 | `AT-B11TEN-1`…`6`, `AT-B11KEY-2` |
| `B11-D-A006` | How many state machines, and what are the states? | **Four**, 15 states total: the frozen five-state `FileAsset` lifecycle (adopted unchanged); an orthogonal five-state storage-object disposition; a two-state attachment lifecycle; a three-state reconciliation case. Six candidate states from the brief were considered and rejected by name | One enum cannot represent "access is revoked but the bytes are still there," which is the exact state §20 requires must never grant access. Separation is what makes `ORPHAN_DELETION_SAFETY_GAPS` and the delete-resurrection guarantee structural rather than procedural | `B11_FILE_LIFECYCLE.md` §1–§6 | `AT-B11LC-1`…`5`, `AT-B11DEL-6` |
| `B11-D-A007` | Application-proxied, direct-to-storage, or hybrid upload? | **Application-proxied (A) for Phase 1**, with `supports_presigned_upload()` on the port so B/C is a later adapter swap changing no state machine, command, DTO, or test | Every integrity property this pack promises is *derivable* under A and merely *asserted* under B. Under B they would rest on a provider capability this pass could not verify (`B11-X-001`, `B11-X-007`), and inventing it is what §27 forbids | `B11_UPLOAD_MODEL.md` §1, `B11_STORAGE_PROVIDER_BOUNDARY.md` §2 | `AT-B11UP-2`, `AT-B11PROV-3` |
| `B11-D-A008` | Is the upload intent a separate aggregate, and when does a file become usable? | **One aggregate.** The intent *is* the `FileAsset` in `pending`, with a `FILE-*` from the first instant and `upload_expires_at` bounding it. **Only a committed `FinalizeUpload` makes a file `available`**, and nothing that is not `available` is attachable or downloadable | A separate intent aggregate would mean two identities for one thing, a second prefix, and a hand-off transaction that can half-fail — reintroducing the orphan class the split was meant to prevent. Same reasoning as `B10-D-A004`'s single-table choice | `B11_DOMAIN_MODEL.md` §3, `B11_UPLOAD_MODEL.md` §2–§3 | `AT-B11UP-3`, `AT-B11UP-4`, `AT-B11UP-5` |
| `B11-D-A009` | What checksum, computed by whom, trusted when — and is an ETag one? | **SHA-256**, lowercase hex, computed **by the application over the received stream**, written once at finalize, **never updated**. A provider ETag is stored as an opaque change hint and is **never** an integrity authority | AWS's own S3 API reference states an ETag "may or may not be an MD5 digest" and is never one for multipart uploads (`B11-X-002`, `VERIFIED`) — so an ETag check fails silently on exactly the large objects most worth checking. Rewriting a stored hash to match a changed object would turn integrity detection into integrity laundering | `B11_CHECKSUM_INTEGRITY.md` §1–§5 | `AT-B11INT-1`…`5` |
| `B11-D-A010` | How is content type determined? | **Three columns, never collapsed:** `declared_content_type` (client claim, evidence only), `detected_content_type` (server inspection, the finding), `content_type` (canonical, the only one any DTO exposes — **never null**: the validated provisional allow-list member while `pending`, overwritten once at finalize with the verified detected type, so the frozen required `FileAsset.content_type` is satisfiable in every lifecycle state). A declared-vs-detected group mismatch is a **rejection**, not a silent correction | Silently accepting the detected type of a file disguised as another is the classic stored-XSS path; trusting the declared type is the "servers implicitly trust the `Content-Type` header" flaw (`B11-X-005`). Extension is a third, weaker cross-check, never a gate | `B11_FILE_VALIDATION.md` §3–§3.1, §4 | `AT-B11VAL-1`, `AT-B11VAL-4`, `AT-B11VAL-8`, `AT-B11VAL-9`, `AT-B11VAL-10`, `AT-B11UP-7`, `AT-B11UP-8` |
| `B11-D-A011` | How are filenames handled? | NFC-normalized; control characters, line separators, and bidi overrides stripped; path separators and `.`/`..` **rejected outright**; ≤255 UTF-8 bytes; empty-after-normalization rejected with **no server-generated fallback**. Stored as display data only — never a key, never a type source, never an access input. `Content-Disposition` carries an ASCII-safe `filename` plus RFC 5987 `filename*` | The product's own fixtures use Arabic filenames (`FB-B11-003`), so the answer had to preserve RTL text while removing bidi *control* characters — banning the character set would have broken legitimate input, and doing nothing leaves the `report.<RLO>gpj.exe` display attack open | `B11_FILE_VALIDATION.md` §5 | `AT-B11VAL-5`…`7`, `AT-B11SEC-2`, `AT-B11SEC-6` |
| `B11-D-A012` | Are duplicate uploads deduplicated by checksum? | **Never.** Checksum equality means the bytes match, not that the business asset is the same. Two intentional uploads of identical bytes produce two `FILE-*`, two objects, two quota charges, two lifecycles. The frozen `checksum` index serves integrity and reconciliation only | Sharing one object between two workspaces would mean one tenant's delete affects another's file — a cross-tenant defect dressed as an optimization. Ownership, permission, retention, and deletion rights are all independent of byte equality | `B11_UPLOAD_MODEL.md` §5, `B11_CHECKSUM_INTEGRITY.md` §6 | `AT-B11DUP-1`, `AT-B11DUP-2` |
| `B11-D-A013` | What is B11's idempotency model, and what is an error versus a replay? | Platform `Idempotency-Key` for `CreateUpload`/`ImportFileFromUrl`; **durable database guards** for everything else. A repeated finalize, attach, or delete is an **idempotent replay**, not an error; only a request that *contradicts* committed state is `409 CONFLICT`. No Redis key participates | Making the commonest retry an error pushes every client into treating success as failure. This is why `UPLOAD_ALREADY_FINALIZED` and `FILE_ALREADY_DELETED` were rejected as codes | `B11_IDEMPOTENCY_CONCURRENCY.md` §1, `B11_FAILURE_CATALOG.md` §3 | `AT-B11IDEM-1`…`5`, `AT-B11ATT-2` |
| `B11-D-A014` | How does a `FileAsset` connect to domain objects? | **Hybrid.** A B11-owned `file_attachments` link table with a **closed two-value `subject_type` enum** in *every* case, as B11's own reference count; plus the subject domain's own explicit field where a frozen contract established one (`MessageMedia.file_asset_ref`). **Not** nullable FKs on `file_assets`. Attach/detach mint **no** permission — they compose `file.upload` with the subject domain's write permission | Frozen `BACKEND_DOMAIN_OWNERSHIP.md` forbids cross-context ORM access, so without its own reference record B11 could not learn whether a file is still in use without violating that rule. `subject_id` is polymorphic and deliberately not a database FK, following the `RevenueEvent.source_ref` / `tax_invoices.source_ref` house pattern | `B11_DOMAIN_ATTACHMENT_MODEL.md` §1–§6, `B11_RBAC_TENANCY.md` §4 | `AT-B11ATT-1`…`6`, `AT-B11CRM-1` |
| `B11-D-A015` | How is deletion represented? | **Soft-delete metadata (`archived`) + asynchronous physical purge; the archived row IS the tombstone.** No `file_assets` row is ever hard-deleted in Phase 1 — not by any command, sweeper, worker, or operator | A separate tombstone table would duplicate every field the archived row already carries, including the storage key the purge worker needs. Retaining the row is what keeps "was there ever a file here" answerable after an abuse report | `B11_DELETION_RETENTION_MODEL.md` §1–§2.1 | `AT-B11DEL-1`…`5`, `AT-B11DEL-7`, `AT-B11IDEM-4`, `AT-B11QUO-7` |
| `B11-D-A016` | Can a provider delete failure resurrect application access? | **No, structurally.** `archived` has no exit transition anywhere in this pack, and `PurgeFileObject` writes no lifecycle field at all. A file stuck in `purge_failed` forever is exactly as inaccessible as one purged in a second | §20's requirement is met by making the two concerns orthogonal rather than by adding a check that a future refactor could remove | `B11_FILE_LIFECYCLE.md` §3 (invariants L-1, L-2), `B11_DELETION_RETENTION_MODEL.md` §3 | `AT-B11DEL-6`, `AT-B11LC-2`, `AT-B11B12-4` |
| `B11-D-A017` | Is an unattached `available` file garbage? | **No.** Auto-cleanup of an `available` file requires **four** conditions: `available`, `retention_class='product'`, **no attachment row has ever existed**, and past `ORPHAN_GRACE`. A file whose attachments are all `detached` (`O-4`) is **never** auto-swept; a provider object with no row (`O-6`) is **never** auto-deleted | Uploading before attaching is the normal sequence in B5's own frozen outbound flow. And an `O-4` file is evidence of a deliberate human act that may itself be under review; an `O-6` finding is as likely to be a lost row as a leaked object, and deleting it in that case destroys a customer's only copy | `B11_ORPHAN_CLEANUP_MODEL.md` §1–§4 | `AT-B11ORP-3`…`6` |
| `B11-D-A018` | How is the storage key formed, and can it change? | `<env>/w/<workspace_uuid>/<yyyy>/<mm>/<file_uuid>` — a pure function of two server-generated UUIDs and a UTC date. **No client string in any position. No extension. Allocated once inside the `CreateUpload` transaction and immutable forever** | Immutability is what makes unknown-outcome handling safe: a retried write, a retried delete, and a post-timeout `stat` all address the identical object, so no retry can create a second one. Path traversal is impossible because there is no user string to sanitize | `B11_STORAGE_KEY_MODEL.md` §1–§3 | `AT-B11KEY-1`…`3`, `AT-B11UNK-1`, `AT-B11UNK-3`, `AT-B11SEC-1` |
| `B11-D-A019` | What is the concurrency model? | **PostgreSQL row locks and unique constraints exclusively.** `SELECT … FOR UPDATE` on `file_assets` for every transition and on `workspace_storage_usage` for every byte accounting; `expected_version` on the two operator commands; partial unique indexes for attachment and case identity; a fixed lock order (usage row **before** file row) making deadlock between B11 commands structurally impossible. **No Redis lock anywhere** | Frozen `BACKEND_DATA_GOVERNANCE.md` prefers constraints and `transaction.atomic` before distributed locks, and `B8-D-A021`/`C11` already established that financial-adjacent uniqueness must not rest on Redis | `B11_IDEMPOTENCY_CONCURRENCY.md` §2–§5 | `AT-B11IDEM-2`…`4`, `AT-B11RACE-1`…`5`, `AT-B11QUO-5` |
| `B11-D-A020` | Who owns storage limits, and when is quota checked? | **B8 owns entitlement truth without exception.** Phase 1 has no storage entitlement metric, and **B11 does not create one**. B11 enforces a uniform, plan-independent **platform safety ceiling** and returns the frozen `403 QUOTA_EXHAUSTED`. Quota is checked at **both** points: advisory at intent (declared size), **authoritative at finalize** (measured size), under a row lock including in-flight reservations | Intent-only checking is bypassed by understating the size; finalize-only checking wastes unbounded bandwidth. Filing a sixth B8 metric would mean inventing per-plan allowances with no product input and no frontend evidence (`FB-B11-011`) | `B11_BILLING_QUOTA_BOUNDARY.md` §1–§4, `B11_STORAGE_USAGE_MODEL.md` §4 | `AT-B11QUO-1`…`6`, `AT-B11B8-1`…`5` |
| `B11-D-A021` | What counts as storage usage? | **Two figures, never assumed equal.** Logical/product usage: `available` + `quarantined`, `product`-class only. Physical/provider usage: everything with bytes `present`, including `pending`, `failed`, `archived`-not-yet-purged, and `legal`-class artifacts. `pending` holds a separate in-flight reservation and counts toward neither total | Assuming equality would either bill a customer for bytes they cannot reach or hide real capacity consumption from operations. The divergence during a pending purge is routine and correct, not a defect | `B11_STORAGE_USAGE_MODEL.md` §1, §3, §5 | `AT-B11QUO-4`, `AT-B11QUO-7`, `AT-B11USE-1`, `AT-B11USE-2` |
| `B11-D-A022` | How are downloads authorized, and are files public? | **Private by default, and Phase 1 has exactly one `access_class` value.** Every byte response re-runs the full chain — session → workspace → R-1 resolution → `file.download` → `available` → ticket — at request time. The ticket is single-use, 5-minute, workspace- and actor-bound, and is the **weakest** gate, not a bearer credential. No provider-signed URL is issued in Phase 1 | §14's rule that a historical URL must never permanently grant access is met by making the ticket incidental: an unauthenticated request with a valid ticket is `401`, and a downgraded actor with a valid ticket is `403`. This also satisfies frozen `B1_AUTHORIZATION_RBAC.md` §4 literally, with no amendment | `B11_RBAC_TENANCY.md` §5, `B11_SECURITY_PRIVACY.md` §5–§6 | `AT-B11DL-1`…`6`, `AT-B11PROV-3` |
| `B11-D-A023` | How are retention classes and legal artifacts handled? | `retention_class ∈ {product, legal}`, set at creation and **immutable in both directions**. Only `product` is ever deleted, swept, or purged. A `legal`-class file is undeletable by **any** command, worker, timer, or operator — including `DeleteAsset`, which returns `403`. B11 asserts **no** statutory period | The exact legal retention is unresolved (`B11-X-008`) and B10 records the same gap independently (`B10-D-B004`). "Never delete" is correct under **every possible answer**, so the design does not depend on the value. Immutability closes the obvious attack of relabelling a statutory record to make it sweepable | `B11_TAX_DOCUMENT_BOUNDARY.md` §1, §3–§4 | `AT-B11TAX-3`, `AT-B11TAX-4`, `AT-B11TAX-5` |
| `B11-D-A024` | Does WazLink scan uploads for malware? | **No, not in Phase 1** — and this pack claims otherwise nowhere. Six compensating controls are enumerated, `quarantine` has a working Phase-1 producer (operator hold), and the future scanner's integration point is a single `FinalizeUpload` step requiring no DTO, table, state, or event change | Frozen `BACKEND_SECURITY_ARCHITECTURE.md` says "malware scanning **where available**," so deferring is contract-compliant. But B5's frozen handoff says it "inherits B11's" scanning policy, which would read as a promise B11 never made — hence `B11-AM-007`, filed rather than left implied | `B11_FILE_VALIDATION.md` §8, `B11_CONTROLLED_AMENDMENTS.md` #7 | `AT-B11LC-3`, `AT-B11LC-5`, `AT-B11SEC-7`, `AT-B11VAL-8` |
| `B11-D-A025` | How is provider media represented, and who owns Message truth? | **Three identities, none substitutable:** Meta's `provider_media_id` (B5), B5's message-scoped `media_id`, and B11's `FILE-*`. A provider media ID is **never** a WazLink file identity. B5 keeps Message, Conversation, delivery status, provider message identity, and every `MessageMedia` field; B11 writes none of them | Frozen `B5_MEDIA_B11_HANDOFF.md` §2 already fixes the field ownership; conflating a provider handle with a durable identity would make WazLink's identity expire when the provider's does | `B11_MESSAGING_MEDIA_BOUNDARY.md` §2–§3 | `AT-B11MSG-1`…`5` |
| `B11-D-A026` | How is upload-from-URL made safe? | `ImportFileFromUrl` is **system-actor-only with no `/api/v1/` surface**, host-allow-listed, refuses off-allow-list redirects, rejects private/loopback/link-local addresses **after DNS resolution**, is bounded by the frozen 10m job deadline and `MAX_FILE_BYTES`, and produces an ordinary `FileAsset` through the same validated path — no privileged shortcut | B5's frozen handoff requires the capability; exposing it to clients would be a server-side request forgery surface handed to every workspace member. Frozen `BACKEND_SECURITY_ARCHITECTURE.md` already mandates allow-lists and SSRF defenses for provider URL fetches | `B11_UPLOAD_MODEL.md` §6, `B11_SECURITY_PRIVACY.md` §2 | `AT-B11MSG-3` |

`CLASS_A_DEFINED = 26`, `CLASS_A_UNRESOLVED = 0`.

| ID | Question | Status | Why it is safe to defer |
|---|---|---|---|
| `B11-D-B001` | Should storage become a product entitlement (a sixth B8 quota metric)? | **deferred to B8/product**; no amendment filed | B8's own §8 says a sixth metric needs its own controlled amendment, and neither the frozen catalog nor the frozen frontend (`FB-B11-011`) has any storage allowance to consume. `B11_BILLING_QUOTA_BOUNDARY.md` §4 pre-specifies the four-step adoption path, in which B11 changes exactly one line |
| `B11-D-B002` | Automated malware/AV scanning | **deferred**, integration point fully specified | the `quarantined` state, the `pending → quarantined` transition, the operator release path, and the audit trail all already exist and are exercised. | `B11-D-B003` | Serving user content from a separate origin (sandbox domain) | **deferred** | a recognized further hardening (`B11-X-004`), but the Phase-1 control is complete without it: active-content types are excluded at ingest, so no such file is ever served to be sandboxed |
| `B11-D-B004` | Direct-to-storage (pre-signed) upload adapter | **deferred**, gated on `B11-X-007` | the port's `supports_presigned_upload()` predicate is the whole switching mechanism; adopting it changes no state machine, command, DTO, table, or acceptance test |
| `B11-D-B005` | A client-facing file list/browse endpoint | **deferred** | the frozen frontend has no file-management surface, and `BACKEND_API_STANDARD.md` restricts filtering to two catalog-marked collections. Adding one later is purely additive |
| `B11-D-B006` | Image derivatives, thumbnails, transcoding | **deferred** | every avatar in the product is a first-letter initial and every image is one static build asset (`FB-B11-007`, `FB-B11-008`). | `B11-D-B007` | Exact production values for `MAX_FILE_BYTES`, `WORKSPACE_STORAGE_SAFETY_CEILING_BYTES`, `UPLOAD_INTENT_TTL`, `DOWNLOAD_TICKET_TTL`, `ORPHAN_GRACE`, `PURGE_GRACE` | **`PRODUCT DECISION REQUIRED`**; proposals with stated reasoning only | nothing in the model breaks at any value; only the storage-cost/recovery-window trade-off moves. `MAX_FILE_BYTES`'s true floor depends on `B5-X-009`, which B5 has not resolved, so deriving it here would be inventing |
| `B11-D-B008` | CRM attachment subject types (Lead, Contact, Note, Task, Appointment, Deal) | **deferred, honoring frozen B2** | `B2_LEAD360_READ_MODEL.md` and `B2_DOMAIN_OWNERSHIP.md` both declare CRM attachments out of Phase-1 scope and mark them "360 (Phase 2)." Registering them would contradict a closed phase. Registration later is one enum value plus three declarations |
| `B11-D-B009` | The statutory retention period for `legal`-class artifacts | **`UNRESOLVED`** (`B11-X-008`); B10 records the identical gap as `B10-D-B004` | B11's fail-safe is structural, not numeric: never deleting a `legal`-class file is correct under every possible answer, so the design cannot be wrong about a value it never uses |
| `B11-D-B010` | Application-layer encryption at rest | **deferred**; no at-rest guarantee is claimed | the deployed target's at-rest behavior is part of `B11-X-007`. Claiming a guarantee that was not verified would be worse than deferring one |
