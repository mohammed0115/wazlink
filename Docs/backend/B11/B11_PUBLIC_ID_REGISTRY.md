# B11 — Public ID Registry

> Design only. **`B11` mints zero new public-ID prefixes.**

## 1. The prefix already exists

Frozen `BACKEND_PUBLIC_ID_REGISTRY.md` section A already registers:

| Prefix | Resource/entity | Owning domain | Persistence concept | Uniqueness |
|---|---|---|---|---|
| `FILE-` | FileAsset | Files | FileAsset | Workspace-scoped |

> **`B11-D-A004`.** B11 reuses `FILE-` verbatim for every `FileAsset`, in every lifecycle state, of every content type, under every retention class, for every attachment subject. No variant prefix, no sub-namespace, no suffix convention.

The registry's own rules apply unchanged: `public_id = FILE-<opaque immutable token>` generated by the canonical UUIDv7/public-ID service; not derived from a filename, checksum, storage key, or provider identifier; stored once at creation with a unique constraint; immutable thereafter; collision handled as a transactionally retried unique-constraint failure.

## 2. Why no second prefix is needed

The brief (§6) instructs review before minting, and warns against assuming one is required. Three candidates were considered:

| Candidate | Verdict | Reason |
|---|---|---|
| An upload-intent prefix (e.g. `UPL-`) | **rejected** | there is no separate intent aggregate. The intent *is* the `FileAsset` in `pending` (`B11_DOMAIN_MODEL.md` §3), so it already has a `FILE-*` from its first instant. A second identity for one row is precisely the conflation that creates orphans |
| An attachment prefix (e.g. `FAT-`) | **rejected** | `file_attachments` is a child row reached through its file or its subject, never addressed independently across a request boundary — the same class as B5's `MessageMedia.media_id` (`med_…`, explicitly "no top-level public-ID prefix, reached only through the owning Message"). Its `attachment_id` in the DTO is the internal UUID, not a registered public identity |
| A reconciliation-case prefix | **rejected** | an operator-only internal record with no cross-domain reference and no client-facing surface. `AuditLog`'s `AUD-*` and the case's own UUID cover every real need |

## 3. Prefixes B11 must never use as identity

| Value | Why it is not a WazLink file identity |
|---|---|
| `provider_media_id` (Meta's) | a provider handle with a provider lifetime (`B11_MESSAGING_MEDIA_BOUNDARY.md` §2). Never written to `public_id`, never a lookup key, never in a storage key |
| `provider_etag` | opaque provider metadata, not guaranteed to be a hash of anything (`B11_CHECKSUM_INTEGRITY.md` §5) |
| `storage_key` | an address, not an identity; operator-visible only |
| `checksum` | content equality is not asset identity (`B11-D-A012`) |
| any URL | never identity, in any form (`B11-D-A003`) |

`FILE_ID_PROVIDER_ID_CONFLATIONS = 0` rests on this table. Negative control `AT-B11MSG-4`.

## 4. Cross-domain invariant, added in B11's own terms

Consistent with the frozen registry's closing "Cross-domain invariants" paragraph: **a `FILE-*` never implies anything about the subject it is attached to.** `FILE-*` does not imply a `MSG-*` was delivered, a `TAX-*` was cleared, an `INV-BILL-*` was paid, or a `REV-*` exists. It implies exactly one thing: bytes with a recorded checksum exist under WazLink's control in one workspace.

`B11` requires **no amendment** to `BACKEND_PUBLIC_ID_REGISTRY.md`.
