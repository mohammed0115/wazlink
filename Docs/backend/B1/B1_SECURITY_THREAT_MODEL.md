# B1 — Tenant & Identity Threat Model

> **B1 status:** Threat analysis only. Controls are design requirements for the future implementation agent, not implementations.

Inherited from `BACKEND_SECURITY_ARCHITECTURE.md`: RBAC enforced in application services (not only UI), allow-listed serializer fields, size-limited validated inputs, ORM parameterization, output escaping, logs that omit passwords/tokens/authorization headers, and mandatory security testing for IDOR, cross-workspace access, permission escalation, quota bypass, injection, mass assignment, webhook signature, and idempotency replay.

| # | Threat | Attack | Control | Error behavior | Audit signal | Test case |
|---|---|---|---|---|---|---|
| T1 | **IDOR** | Authenticated member of W1 requests a `LEAD-*`/`MEM-*`/`WINV-*` belonging to W2 | Doctrine R-1: every tenant-owned read goes through `for_workspace(active_workspace)`; object resolution (step 9) happens *after* tenant scoping and *after* RBAC | `404 ENTITY_NOT_FOUND` — byte-identical to a non-existent ID | `authz.object_not_in_scope` with the attempted public ID and the active workspace | Seed the same object type in W1 and W2; as a W1 Owner request the W2 ID; assert `404`, assert the response body is identical to a random-ID request, assert no row was read into the response |
| T2 | **Tenant escape via path/header/body** | Caller sends `/workspaces/{W2}/members`, or a body/header `workspace_id=W2`, while their session is on W1 | Doctrine R-3: the path segment is *validated against*, never substituted for, `sessions.active_workspace_id`; body/header workspace fields are not read by the pipeline at all | `404 WORKSPACE_NOT_FOUND` even when the caller is a member of W2 | `authz.workspace_path_mismatch` | For every `{workspace_id}` route, call with a workspace the caller *is* a member of but is not switched to; assert `404` and no data from W2 |
| T3 | **Privilege escalation (self)** | A Member `PATCH`es their own membership to `role=owner` or `admin` | Role-mutation guards: never self, never at/above own rank, never `owner` via `PATCH`; `role` is not client-writable on self | `403 PERMISSION_DENIED` | `authz.role_change_denied` | As each of the six roles, attempt self-promotion to each other role; assert 36 denials and zero writes |
| T4 | **Privilege escalation (lateral)** | An Admin grants themselves `owner` by inviting a second account and transferring | `role <> 'owner'` check on invitations; `ownership.transfer` is Owner-only; rank guard blocks granting at/above own rank | `403 PERMISSION_DENIED` / `400 VALIDATION_ERROR` on `role="owner"` in an invite | `authz.invite_role_denied` | Invite with `role="owner"`; assert `400`. As Admin call ownership-transfer; assert `403` |
| T5 | **Session fixation** | Attacker plants a known session cookie, victim logs in with it | The session key is **rotated on every successful login**; the pre-auth Django session is destroyed and no registry row is carried over | pre-auth cookie becomes `401 AUTH_REQUIRED` | `auth.login_succeeded` records a new `SES-*` | Capture the pre-login cookie, log in, replay the pre-login cookie; assert `401` and that the `SES-*` in the login response differs |
| T6 | **Session theft (XSS/network)** | Cookie exfiltrated and replayed | `HttpOnly` + `Secure` + host-only `Domain`; absolute expiry never extended; per-session revocation surface; output escaping and CSP inherited from B0 | replay works until expiry or revocation — bounded by the 24h absolute cap | `SessionCreated`/`SessionRevoked` with `ip_hash` + `user_agent_digest` change | Assert the cookie is unreadable from JS; assert absolute expiry is not extended by activity; revoke from another session and assert the stolen cookie yields `401 SESSION_REVOKED` |
| T7 | **CSRF** | Cross-site form/fetch performs an unsafe request with the ambient cookie | CSRF token required on every unsafe cookie-authenticated request (B0 mandate) + `SameSite=Lax` as defence in depth | `403` (CSRF layer, before the pipeline) | `security.csrf_rejected` | For every unsafe B1 route, send a valid session cookie without a CSRF token; assert rejection and no state change |
| T8 | **Invitation token theft** | Token read from an API response, a log, an audit record, an event payload, or an error message | The raw token is returned by **no API response** (`B1_API_DTO_CONTRACTS.md` §3.1); it exists in cleartext only inside the issuing transaction and in the outbound email to the invited address; storage is `sha256` of a ≥256-bit CSPRNG value; catalog §3.3 bans it from payloads, outbox rows, Celery arguments, logs, and audit | n/a | `invitation.created` contains `WINV-*` only | Automated scan: assert no API response body, log line, audit row, outbox row, Celery argument, or error body in the invitation flow contains the raw token value |
| T9 | **Invitation replay** | The same token is submitted twice, or after cancel/expiry | Single-use consumption under `FOR UPDATE`; `token_hash` nulled on every terminal transition; expiry evaluated inline at acceptance | `409 INVITATION_ALREADY_ACCEPTED` / `INVITATION_CANCELLED` / `INVITATION_EXPIRED` | `invitation.accept_rejected` with the reason | Accept twice; accept after cancel; accept after expiry; assert exactly one `MEM-*` exists in all three |
| T10 | **Invitation token brute force** | Enumerating token space | ≥256-bit CSPRNG token; unknown token ⇒ `404` identical to malformed; per-IP rate limit on `/invitations/accept` | `404 ENTITY_NOT_FOUND`, then `429 RATE_LIMITED` | `auth.invitation_token_rejected`, rate-limit counter | Submit N random tokens; assert uniform `404` then `429`; assert no timing difference between "wrong token" and "token for another workspace" |
| T11 | **Email enumeration** | Probing login / register / password-reset to learn which addresses exist | Constant-time credential comparison against a dummy hash for unknown users; `202` for register and reset regardless of existence; identical `401 INVALID_CREDENTIALS` for unknown-email, wrong-password, and disabled | `401` / `202` uniformly | `auth.login_failed` (server-side only; never reflected to the caller) | Statistical timing test over 1000 known vs unknown addresses; assert no separable distribution and byte-identical bodies |
| T12 | **Role-escalation race** | Two concurrent role changes, or a role change interleaved with the target's own privileged request | `FOR UPDATE` on the membership + `If-Match`; no authorization caching, so the role is read in the same transaction as the write | loser gets `409 STALE_VERSION` | `membership.role_changed` with before/after | Fire N concurrent role changes; assert exactly one commit, `version` incremented by exactly 1, and the final role is one of the submitted values |
| T13 | **Owner-removal race** | Two Owners simultaneously remove/demote each other, leaving zero Owners | INV-WS-1 re-evaluated **under the row lock** inside each transaction; ordered locking for two-row commands | one succeeds, the other `409 LAST_OWNER_REQUIRED` | `membership.removed` / `authz.last_owner_blocked` | Two Owners, simultaneous mutual removal, 100 iterations; assert active-Owner count is never 0 |
| T14 | **Stale membership** | A removed member's in-flight or subsequent request still succeeds | Membership re-read at pipeline step 6 inside the request transaction; on removal the session re-resolves or is revoked | `403 MEMBERSHIP_INACTIVE` / `404 WORKSPACE_NOT_FOUND` / `401 SESSION_REVOKED` | `session.workspace_reresolved` / `session.revoked_no_workspace` | Remove a member mid-flight; assert the next request is denied without any new login |
| T15 | **Stale permission cache** | A demoted user keeps elevated access from a cached decision | **No authorization caching exists** (B0 governance prohibition). Membership, role, matrix version, entitlement, and quota are read per request | immediate `403 PERMISSION_DENIED` | `membership.role_changed` then `authz.permission_denied` | Demote Admin→Viewer, then immediately issue an admin-only request on the *same* session; assert `403` with no re-login and no delay |
| T16 | **Cross-workspace relationship injection** | Creating a Deal in W1 that references a Lead/Pipeline/Stage in W2 | Doctrine R-2: every referenced resource is resolved through the same active-workspace scope and its `workspace_id` must equal the active workspace | `404 ENTITY_NOT_FOUND` for the reference (never `400`, which would confirm existence) | `authz.relationship_out_of_scope` | For each relationship in the R-2 table, submit a cross-tenant ref; assert `404` and that no row was created |
| T17 | **Mass assignment** | Posting `workspace_id`, `status`, `public_id`, `version`, `email_verified_at`, or `role` on a self-update | Doctrine R-4: `additionalProperties: false` on every request DTO; unknown fields rejected, not ignored; server-generated fields are not in any request allow-list | `400 VALIDATION_ERROR` naming the rejected field | `security.unknown_field_rejected` | For every B1 request DTO, submit each forbidden field; assert `400` and zero mutation |
| T18 | **Brute-force login** | Password guessing against one account or spraying across many | B0 limits `10/min/IP` **and** `5/min/account`; `failed_login_count` drives alerting | `429 RATE_LIMITED` + `Retry-After` | `auth.login_failed` count, `security.rate_limited` | Exceed both limits independently; assert `429` with `Retry-After` and that the account limit triggers even from rotating IPs |
| T19 | **Credential stuffing** | Reusing breached credentials at scale | Per-account limit (not just per-IP); breached-password check at register/change/reset; `UserPasswordChanged` and anomalous `SessionCreated` feed security monitoring | `429` / `400 VALIDATION_ERROR` on a breached password | `security.credential_stuffing_suspected` | Distributed low-rate attempts across many accounts from many IPs; assert the per-account limiter and the monitoring signal both fire |
| T20 | **Session replay after logout** | Replaying a cookie captured before logout | Logout revokes the registry row **and** destroys the Django session in one transaction; validation step 2 requires an `active` registry row | `401 SESSION_REVOKED` | `auth.logout` | Capture the cookie, log out, replay; assert `401 SESSION_REVOKED` |
| T21 | **Workspace-existence oracle via switching** | Iterating `WORK-*` values through `SwitchWorkspace` | Not-eligible and not-existent both return `404 WORKSPACE_NOT_FOUND`; the endpoint is rate-limited | `404` uniformly | `session.workspace_switch_denied` | Switch to a real workspace the caller does not belong to, and to a random `WORK-*`; assert identical status, body, and timing distribution |
| T22 | **Cross-tenant denial of service via membership removal** | A W1 admin removes a user to log them out of W2 | Membership removal never revokes sessions unless the user is left with **zero** eligible workspaces; the session re-resolves to a remaining workspace instead | user stays signed in, W1 simply disappears from `GET /workspaces` | `session.workspace_reresolved` | Member of W1+W2 active on W1; remove from W1; assert the same session continues on W2 without re-login |
| T23 | **Session enumeration across users** | Requesting another user's `SES-*` | `GET /auth/sessions` is scoped by `user_id`; revoke resolves within the caller's own sessions only | `404 ENTITY_NOT_FOUND` | `auth.session_revoke_denied` | As user A, revoke a valid `SES-*` of user B; assert `404` and that B's session still works |
| T24 | **Operator/admin bypass** | Django Admin used to mutate tenant data outside the pipeline | B0: "Admin access is internal operational access, not a bypass of audit, tenant, or financial controls"; operator actions are separate commands (`DisableUser`, workspace recovery) with their own audit | n/a | `operator.*` audit actions with an operator principal | Assert every operator-capable mutation writes an audit row with a distinguishable operator actor, and that no tenant role can invoke it |
| T25 | **Global lockout via tenant action** | A W1 admin suspends or removes a single-workspace user's only membership, intending (or incidentally causing) to lock them out of the product entirely, or to strand a global identity with no recovery path | Two controls. **(a)** `SuspendMembership` on the target's final eligible membership is refused `409 CONFLICT` · `last_active_membership` under a locked eligible-membership count (`B1_WORKSPACE_MEMBERSHIP_MODEL.md` §3.1). **(b)** `RemoveMember` is permitted — a tenant must be able to evict its own member — but the User's **global account stays `active`**, login still succeeds into a no-workspace session, and `POST /invitations/accept` and `POST /workspaces` remain reachable. No tenant role can reach `users.status` (`B1-D-A17`). | `409 CONFLICT` on suspend; `200` + `workspace_ref: null` on the subsequent login | `authz.last_active_membership_blocked`; `session.revoked_no_workspace`; `auth.login_succeeded` with `details.no_eligible_workspace = true` | Single-workspace user: assert suspend is refused with no mutation; assert remove succeeds, `users.status` is still `active`, the next login returns `200` with `workspace_ref: null`, every tenant route returns `404 WORKSPACE_NOT_FOUND`, and accepting a fresh invitation restores full access |
| T26 | **Password-reset / verification token brute force** | Enumerating the `user_email_tokens` token space to seize an account without the password, or replaying a consumed reset link | **≥256-bit CSPRNG** opaque token, stored only as `sha256` (`B1_IDENTITY_DATA_MODEL.md` §2); single-use with `consumed_at`; short expiry (reset 60min, verification 72h); `token_hash` nulled on consumption or expiry; issuing a new token supersedes all prior unconsumed tokens of that purpose; per-IP and per-address rate limits on request and confirm | `400 VALIDATION_ERROR` (generic) for invalid, expired, consumed, or unknown — all four indistinguishable; then `429 RATE_LIMITED` | `auth.password_reset_completed` / `security.rate_limited`; the raw token never appears in any audit row | Submit N random reset tokens; assert uniform `400` with byte-identical bodies then `429`; replay a consumed token and assert `400`; assert entropy ≥256 bits at the generator; scan logs, audit, outbox, and Celery arguments for the raw value and assert zero occurrences |

## 26-threat coverage summary

Each of the 26 threats has a control that is either inherited verbatim from B0 or introduced by an explicit B1 doctrine (R-1…R-4, INV-WS-1, INV-USER-1, no-caching, no-raw-token-in-response). No threat is mitigated only by UI behavior, and none relies on Redis.

**B1-FIX.1 added T25 and T26.** T25 covers the global-lockout class opened by the repaired INV-USER-1 guard set; T26 covers reset/verification token brute force, which the original 24 left uncovered because token entropy was unspecified.
