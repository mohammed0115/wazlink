# B1 — Authentication, Session, and Active-Workspace Resolution

> **B1 status:** Target design only. **No authentication code, middleware, backend, or Django configuration is authorized.**

Inherited: ADR-009 (session-backed authentication for Phase 1; JWT/OAuth/MFA are later phases requiring separate security review), CSRF mandatory for cookie-authenticated unsafe requests, and B0 login rate limits of `10/min/IP` and `5/min/account`.

## 1. Cookie and transport

| Property | Value | Rationale |
|---|---|---|
| Cookie name | **`sessionid`** | the frozen B0 contract declares `securitySchemes.sessionAuth.name = "sessionid"` (`BACKEND_OPENAPI_V1.yaml`). B1 does **not** rename it. *(Non-normative hardening note: an opaque, non-branded cookie name would reduce stack fingerprinting. It is out of B1 scope and would require an explicit B0 amendment; no B1 contract depends on it.)* |
| `HttpOnly` | **yes** | JavaScript can never read the session key; blocks XSS session theft |
| `Secure` | **yes** | HTTPS only |
| `SameSite` | **Lax** | the SPA is same-site; `Lax` blocks cross-site POST CSRF while preserving top-level navigation. `Strict` is not chosen because it breaks the email-link → verify/accept-invitation flows. |
| `Path` | `/` | |
| `Domain` | host-only (attribute omitted) | prevents sibling-subdomain cookie injection |
| CSRF | separate CSRF cookie/header pair on every unsafe request | B0 requirement; `SameSite=Lax` is defence-in-depth, not the primary control |
| Session key | ≥128-bit CSPRNG, generated by the Django session backend | only `sha256(key)` is stored in the `sessions` registry |

## 2. Session policy (Phase 1)

| Policy | Value | Basis |
|---|---|---|
| Idle expiry | **8 hours** of inactivity (`idle_expires_at = last_seen_at + 8h`) | working-day session |
| Absolute expiry | **24 hours** from creation; **never extended** | bounds a stolen cookie's value |
| Persistent "remember me" | **not implemented in Phase 1** | the frozen frontend's own security fixture is `sessionPolicy: "session_only_mock"` and the login checkbox reads "تذكرني في هذه الجلسة" (*within this session*). Persistent sessions are Class C (`B1-D-008`). |
| Concurrent sessions per user | allowed, unlimited, all enumerable and individually revocable | |
| `last_seen_at` write | throttled to at most once per minute | bounds write amplification without weakening idle expiry meaningfully |

The numeric windows are **tunable product values** (`B1-D-007`, Class B). The *mechanism* — dual idle + absolute expiry, non-extending absolute bound, registry-backed revocation — is architecturally closed and must not be changed at tuning time.

## 3. Authentication flows

### 3.1 Login — `POST /api/v1/auth/login` (frozen B0 operation, public)

1. Rate-limit by IP and by submitted account (`10/min/IP`, `5/min/account`). Exceeded ⇒ `429 RATE_LIMITED` with `Retry-After`.
2. Normalize the email; look up a non-deleted User.
3. Verify the password with the Django hasher. **The comparison runs on a dummy hash when the user is absent**, so timing does not disclose account existence.
4. Failure ⇒ `401 INVALID_CREDENTIALS`, identical response for unknown-email, wrong-password, and `disabled` user. Increment `failed_login_count`; audit `auth.login_failed`.
5. Success ⇒ **rotate the session key** (a brand-new Django session; any pre-authentication session is destroyed). This is the session-fixation control.
6. Resolve the active workspace (§4). This step is **total**: it yields either an eligible workspace or `NULL` (§4.2 case 4). It never fails and never blocks login. Create the `sessions` registry row in the same transaction as the Django session.
7. Set `last_login_at`, reset `failed_login_count`, audit `auth.login_succeeded`.
8. Respond `200` with `Session{session_id: SES-*, user: EntityRef(USR-*), workspace_ref: EntityRef(WORK-*) | null, expires_at}`. `workspace_ref` is `null` only in the `|E(U)| = 0` case (§4.2 case 4, `B1-D-A23`).

`expires_at` is `min(idle_expires_at, absolute_expires_at)` — the earliest instant at which the session stops working, which is the only value a client can act on correctly.

Unverified users **do** receive a session (see `B1_WORKSPACE_MEMBERSHIP_MODEL.md` §2); verification is enforced later in the authorization pipeline. This is required to keep the frozen login response set (`200/400/401/429/500`) intact.

### 3.2 Logout — `POST /api/v1/auth/logout` (frozen B0 operation)

Revokes **this** session only: registry row → `revoked(user_logout)` and the Django session destroyed, one transaction. `204`. Idempotent: logging out an already-invalid session still returns `204` (never `401`), so the client can always reach a clean state. Audit `auth.logout`.

### 3.3 Session validation — every authenticated request

In order, inside the request transaction:
1. Cookie present and the Django session decodes ⇒ else `401 AUTH_REQUIRED`.
2. A `sessions` row exists for `sha256(key)` ⇒ else `401 SESSION_REVOKED`.
3. `status='active'` ⇒ else `401 SESSION_REVOKED`.
4. `now < absolute_expires_at` and `now < idle_expires_at` ⇒ else transition the row to `expired`, destroy the Django session, `401 AUTH_REQUIRED`.
5. Slide `idle_expires_at` (throttled). The absolute bound is **never** moved.

`401 AUTH_REQUIRED` and `401 SESSION_REVOKED` are both `401`; the distinction exists for client UX ("session ended" vs "you were signed out elsewhere") and for audit, and neither discloses anything an unauthenticated caller does not already control.

### 3.4 Password change — `POST /api/v1/auth/password-change` (B1-additive)

Requires the **current password** in the request body — that is the re-authentication control for this action and needs no separate step-up mechanism. On success: update the hash, set `password_updated_at`, and revoke **every other** session of the user (`password_change`); the acting session survives and its key is rotated. Audit `auth.password_changed` (no password material, no hash).

### 3.5 Password reset — `POST /auth/password-reset`, `POST /auth/password-reset/confirm` (B1-additive)

Request: always `202`, regardless of whether the address exists — this is the anti-enumeration control. Rate-limited per IP and per address. A single-use `user_email_tokens` row is created; only its hash is stored. Confirm: validates hash, purpose, expiry, and unconsumed state; sets the new password; consumes the token; revokes **all** sessions (`password_change`); audits `auth.password_reset_completed`. Invalid or expired ⇒ `400 VALIDATION_ERROR` with a generic message.

### 3.6 Email verification — `POST /auth/verify-email` (B1-additive)

Consumes a single-use `email_verification` token, sets `email_verified_at`, audits `auth.email_verified`. Re-request is rate-limited and always `202`.

### 3.7 Registration — `POST /auth/register` (B1-additive, public, rate-limited)

Creates the User (`active`, unverified), issues a verification token, and — in the same transaction — creates a Workspace with the registrant as `owner`, so every self-registered User starts with `|E(U)| = 1` (INV-USER-1). Response is always `202` with no body detail that distinguishes "created" from "email already in use"; if the address is already registered, the system sends an account-exists notification instead of creating anything. Audit `auth.registered` (or `auth.register_duplicate_suppressed`).

### 3.8 Global logout — `POST /auth/sessions/revoke-all` (B1-additive)

Revokes every session of the calling user including the current one (`global_logout`). `204`. Idempotent. Audit `auth.sessions_revoked_all` with the count.

### 3.9 Session revocation surface — `GET /auth/sessions`, `POST /auth/sessions/{id}/revoke` (B1-additive)

`GET` lists **only the caller's own** sessions: `SES-*`, `created_at`, `last_seen_at`, `expires_at`, `status`, a coarse `user_agent_label`, and `is_current`. It never returns IP addresses, raw user agents, session keys, or any other user's sessions — the queryset is scoped by `user_id`, so cross-user session enumeration is structurally impossible. Revoking a `SES-*` that is not the caller's returns `404 ENTITY_NOT_FOUND`.

### 3.10 Automatic revocation triggers

| Trigger | Sessions revoked | Reason code |
|---|---|---|
| Password change / reset | all other (change) / all (reset) | `password_change` |
| `DisableUser` | all of that user | `user_disabled` |
| `DeleteUser` | all of that user | `user_disabled` |
| `RemoveMember` | none revoked; the *session's* `active_workspace_id` is re-resolved on the next request (§4.4) | `membership_removed` (only when the session is left with no eligible workspace) |
| `SuspendMembership` | none revoked; the session re-resolves (§4.4). Suspending the target's **final** eligible membership is refused outright (`409 CONFLICT` · `last_active_membership`), so this trigger can never empty `E(U)` | — |
| `DeleteWorkspace` | sessions whose `active_workspace_id` is that workspace | `workspace_deleting` |
| Operator action | targeted | `admin_revoke` |

Membership removal deliberately does **not** kill the user's session for their *other* workspaces. Killing it would let any workspace admin log a user out of unrelated tenants — a cross-tenant denial-of-service.

## 4. Active-workspace resolution

> **The authoritative mechanism is the server-side column `sessions.active_workspace_id`, always re-validated against a live Membership inside the request transaction.**

The client cannot influence tenant selection. A `workspace_id`, `workspace_ref`, path segment, header, query parameter, or resource public ID supplied by the client is a presentation input and is **never** read by the authorization pipeline. The only client-initiated change is the explicit `SwitchWorkspace` command, which is itself authorized against Membership.

### 4.1 Eligibility predicate

A workspace `W` is **eligible** for user `U` when:

```
E(U) = { W : membership(U, W).status = 'active'
             AND W.status IN ('active', 'suspended', 'archived') }
```

**This predicate is canonical.** It is the single definition of eligibility in B1, and it is the same `E(U)` that INV-USER-1 quantifies over (`B1_WORKSPACE_MEMBERSHIP_MODEL.md` §1.1). Any rule elsewhere in the package that speaks of an "eligible workspace" means exactly this set. A `suspended` membership is **not** eligible — membership status must be `active`.

`deleting` is excluded (its memberships are already `removed`). `suspended` and `archived` workspaces are eligible **on purpose**: a member must be able to sign in and see why the workspace is blocked, and an Owner must be able to reach billing to resolve a suspension. Write attempts in those states still fail with `403 WORKSPACE_INACTIVE`.

**Selection priority.** Eligibility answers *may this workspace be selected*; it does not answer *which one to prefer*. For ordering, each eligible workspace carries a priority derived from its own state:

| `W.status` | Priority | Meaning |
|---|---|---|
| `active` | **0 (preferred)** | operationally usable |
| `suspended` | 1 | selectable for recovery/administration only |
| `archived` | 1 | selectable for recovery/administration only |

An operationally usable workspace is always preferred over a recovery-only one (§4.2).

### 4.2 Resolution at login (deterministic)

1. Build the eligible set `E = E(U)` (§4.1).
2. If `|E| = 1` ⇒ that workspace.
3. If `|E| > 1`, apply in order:
   a. If `users.last_active_workspace_id ∈ E` **and that workspace's `status = 'active'`** ⇒ that workspace. A stored hint pointing at a recovery-only workspace does not win over an operationally usable one.
   b. Else, order `E` by the total key **`(priority, memberships.joined_at, workspaces.public_id)`** — `priority` as defined in §4.1 (`active` = 0; `suspended`/`archived` = 1) — and take the first. This prefers an operationally usable workspace over a recovery-only one, then breaks ties deterministically and reproducibly.
   c. If every member of `E` is recovery-only, 3b still selects one, so an archived or suspended workspace remains reachable and its recovery use is preserved.
4. If `|E| = 0` ⇒ **the login still succeeds** with `sessions.active_workspace_id = NULL` and `Session.workspace_ref = null`. See §4.6.

**Why 3a is qualified.** Before B1-FIX.1 the hint won unconditionally, so a user whose last-used workspace had since been archived was deterministically returned to a workspace in which every write fails, even while holding an operationally usable one. The `status = 'active'` qualifier removes that without making archived workspaces unreachable — the user can still switch to one explicitly (§4.3), which is the deliberate recovery path.

### 4.3 Switching — `POST /api/v1/auth/session/workspace` (B1-additive)

Body: `{ workspace_ref: EntityRef }`. Steps:
1. `SELECT … FOR UPDATE` on the caller's `sessions` row.
2. Re-evaluate eligibility for the requested workspace. Not eligible ⇒ `404 WORKSPACE_NOT_FOUND` — **never** `403`, because distinguishing "exists but you're not a member" from "does not exist" is a tenant-enumeration oracle.
3. Set `sessions.active_workspace_id` and `users.last_active_workspace_id`.
4. Respond with the refreshed `Session` DTO.
5. Audit `session.workspace_switched` with `from`/`to` workspace public IDs.

Switching does **not** rotate the session key: the principal is unchanged and no privilege boundary is crossed at the user level. Because no authorization decision is cached, the new workspace's role, entitlements, and quotas take effect on the very next request — this is the concrete implementation of B0's "Switching workspace re-evaluates permission and entitlement context on every request".

**Concurrent switches** to different workspaces both take the row lock; they serialize and the last committed wins. The session ends in exactly one of the two requested workspaces — never a third, never a blend — and both attempts are audited.

### 4.4 Re-validation on every request

The active workspace is re-resolved, not trusted, on each request:

| Situation at request time | Outcome |
|---|---|
| Membership still `active`, workspace eligible | proceed |
| Membership became `suspended` | `403 MEMBERSHIP_INACTIVE`. The session is not revoked and `active_workspace_id` is not re-resolved — suspension is reversible. Because §3.1 forbids suspending a user's final eligible membership, the user always retains at least one other eligible workspace to switch to. |
| Membership became `removed` | fall back: re-resolve using §4.2 over the remaining eligible set. If non-empty, silently switch and audit `session.workspace_reresolved`. If empty, revoke the session (`membership_removed`), audit `session.revoked_no_workspace`, and return `401 SESSION_REVOKED`. The user's **global account stays `active`** and they may sign in again into a no-workspace session (§4.6). |
| Workspace became `suspended`/`archived` | reads allowed per role; unsafe operations `403 WORKSPACE_INACTIVE` |
| Workspace became `deleting` | session revoked (`workspace_deleting`), `401 SESSION_REVOKED` |

### 4.5 Non-request contexts

- **Celery tasks** carry an explicit `workspace_id` in the task payload. A worker never reads a session and never has an "active workspace".
- **Webhooks** resolve the tenant from provider identity (see `B1_WORKSPACE_MEMBERSHIP_MODEL.md` §1.4). A webhook has no user, no session, and no RBAC; it acts as a system principal recorded in audit as `system:webhook`.
- **Outbox dispatch** uses the `workspace_id` stamped on the event at write time.

### 4.6 The no-workspace session (`|E(U)| = 0`)

`|E(U)| = 0` is a **supported product state**, not a defect. It is reachable by exactly one transition: an authorized administrator removing a User's final eligible membership (`B1_WORKSPACE_MEMBERSHIP_MODEL.md` §3.1). Every other transition that could produce it is guarded.

| Aspect | Target semantics |
|---|---|
| `sessions.active_workspace_id` | `NULL` |
| `Session.workspace_ref` | `null` |
| Tenant-scoped operations | every one fails at authorization pipeline **step 5** with `404 WORKSPACE_NOT_FOUND`. No tenant data is reachable. |
| Reachable surface | the non-tenant operations only: `GET /auth/session`, `GET /auth/sessions`, `POST /auth/sessions/*`, `POST /auth/logout`, `POST /auth/password-change`, `GET /workspaces` (returns an empty list), `POST /workspaces`, `POST /invitations/accept` |
| Recovery | `POST /invitations/accept` or `POST /workspaces`. Both are non-tenant-scoped, so both are reachable. |
| Global account | remains `active`; never disabled as a consequence |
| Alerting | none. No `identity.invariant_violation` is raised. |
| Audit | `auth.login_succeeded` with `workspace_id = NULL` and `details.no_eligible_workspace = true` |

**Why login must succeed.** Every recovery path in B1 requires an authenticated session. Refusing login would turn a single tenant administrator's `RemoveMember` into a **permanent lockout of a global identity**, which is exactly the cross-tenant harm `B1-D-A17` and threat T22 exist to prevent. A no-workspace session grants access to nothing tenant-owned, so permitting it costs no isolation.

#### 4.6.1 `Session.workspace_ref` nullability — B1 target amendment (`B1-D-A23`)

**This is a B1 target-contract amendment over frozen B0. B0 does not say this.**

| | |
|---|---|
| **B0 frozen contract** | `Session.workspace_ref` is `$ref: EntityRef`, listed in `required: [session_id, workspace_ref, expires_at]`, and **not** nullable |
| **B1 target** | `workspace_ref` stays in `required` (the key is always present) and becomes `nullable: true` — `{"nullable": true, "allOf": [{"$ref": "#/components/schemas/EntityRef"}]}` |
| **Required set** | **unchanged.** No field is added or removed. |
| **Precedent** | B0 already uses required-and-nullable: `PageInfo.next_cursor` is in `PageInfo.required` and carries `"nullable": true`. The same shape is applied here. |
| **Status** | design decision **closed** (`B1-D-A23`); executing the `BACKEND_OPENAPI_V1.yaml` edit is a gated pre-implementation contract step (`B1-D-019`, Class B) requiring CTO approval. **B1 does not edit the frozen contract.** |

**Why the amendment is necessary rather than convenient.** The frozen non-nullable `workspace_ref` cannot represent a legitimately reachable state, so without it B1 would have to choose between three unacceptable outcomes: forbid a tenant from evicting its last single-workspace member; permanently lock a global identity out of the product; or invent a second authentication mechanism for invitation acceptance. The amendment is the smallest change that avoids all three.

#### 4.6.2 `sessions.active_workspace_id` nullability

The logical column stays **nullable**, and `NULL` is legal in exactly one case: the owning session's User has `|E(U)| = 0`. It is never null for any other reason — not transiently during login (step 6 is total), not pre-authentication (no registry row exists before authentication), and not as an "unset" placeholder.

**Invariant SESS-1.** A session row with `active_workspace_id IS NOT NULL` must reference a workspace that was in `E(U)` at write time, re-validated on every request (§4.4). A session row with `active_workspace_id IS NULL` is **not usable for any tenant-scoped operation**; every such request terminates at pipeline step 5.

## 5. First-login and onboarding

The frozen frontend gates on `onboardingDone` (`services/index.ts:133`). Target authority: the workspace's own profile completeness (`name`, `timezone`, `currency`, `locale` plus the onboarding profile captured by the Onboarding screen), read from `GET /workspaces/{id}`. `onboardingDone` becomes a derived projection over workspace state, not a client-held boolean.
