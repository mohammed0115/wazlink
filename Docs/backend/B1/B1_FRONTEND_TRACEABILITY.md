## Compatibility guarantees

1. **No frozen required set changes, and two narrow amendments.** `Workspace`, `WorkspaceList`, `PageInfo`, `EntitlementDecision`, `EntitlementList`, `UsageDTO`, `Plan`, `PlanList`, `LoginRequest`, and `InviteRequest` are untouched. The two B1 amendments (`B1_API_DTO_CONTRACTS.md` §1.1) are: `Session.workspace_ref` becomes nullable — **the `required` set is unchanged** — and `POST /workspaces/{id}/invitations` returns the new `Invitation` schema instead of the `Workspace` projection. The `Workspace` schema itself is unchanged and still serves `GET /workspaces`.
2. **No frozen vocabulary changes.** Six capability IDs, five usage metrics, four entitlement statuses, three upgrade reasons, three plan codes, six RBAC roles — all preserved verbatim.
3. **Adapter-only frontend migration.** Every change lands behind `sessionService`, `workspaceService`, `entitlementService`, and `settingsFeatureService`. No route, no hash-router change, no domain rewrite — which is exactly the migration path B0 `BACKEND_WORKSPACE_AUTH.md` promised.
4. **Two genuinely new UI surfaces:** the workspace switcher (#9) and the invitation management list with cancel/resend (#16). Both are additive screens, not rewrites. A third, smaller state — the no-workspace shell (#4) — is a single empty-state view, not a screen.
5. **One semantic correction the frontend must make:** `user.role` (job title) must be separated from `Membership.role` (RBAC) — items #14 and #15. This is the only place where frozen frontend vocabulary is actively wrong for the backend target, and leaving it conflated would be a security defect, not a cosmetic one.
