| `B9-D-A012` | **A reversal cannot itself be reversed.** Over-correction is fixed by a new recognition, so the register never acquires signed arithmetic | `B9_REVERSAL_MODEL.md` §2 |

| `B9-D-A014` | **Attribution is snapshotted at recognition time, immutably.** Read-time recomputation is rejected: it would let history change under later Lead/Business edits | `B9_FIRST_TOUCH_MODEL.md` §6 |
| `B9-D-A015` | **Reversal attribution is derived, not snapshotted and not separately compensated.** With 100% first-touch allocation, attributed always equals recognized for an attributed event under both contracts, so the two cannot drift | `B9_ATTRIBUTION_MODEL.md` §6 |
| `B9-D-A016` | **One attribution snapshot per event, `allocation_bps = 10000`.** No generic allocation table in Phase 1 — first-touch has exactly one winner, so no rounding or sum-to-100 failure can occur | `B9_ATTRIBUTION_MODEL.md` §5 |
| `B9-D-A017` | **No FX conversion, no exchange rate, no cross-currency total.** Currency is a grouping key; a scalar total across currencies does not exist | `B9_CURRENCY_MONEY_MODEL.md` §2 |
| `B9-D-A018` | **No look-back window on touchpoints.** The only temporal test is `occurred_at ≤ recognized_at`; revenue months after acquisition still attributes to the original touch | `B9_FIRST_TOUCH_MODEL.md` §5 |
| `B9-D-A019` | **`recognized_at` is the single reporting-period key**, stored UTC, workspace-tz boundaries, half-open ranges. `effective_at` is rejected | `B9_TIME_PERIOD_MODEL.md` §2 |
| `B9-D-A020` | **A reversal corrects the period of the event it reverses**, not the period it was issued in — otherwise a closed period's meaning would depend on when someone noticed | `B9_TIME_PERIOD_MODEL.md` §4 |
| `B9-D-A021` | **WazLink platform billing is categorically not recognizable** as customer revenue; a platform `PAY-*`/`INV-BILL-*` source is rejected `B9-AF-007` | `B9_REVENUE_RECOGNITION_POLICY.md` §5 |
| `B9-D-A022` | **Automation holds no financial authority.** No B7 rule, action, run or approval may invoke any B9 command, with or without approval; `system:automation` holds no B9 permission | `B9_B7_AUTOMATION_BOUNDARY.md` §1 |
| `B9-D-A023` | **A Deal need not be `won`** for a `deal`-sourced recognition. Requiring it would make recognition a function of pipeline state — the exact coupling the firewall forbids. The unusual case is an informational reconciliation signal | `B9_B6_PIPELINE_BOUNDARY.md` §5 |
| `B9-D-A024` | **No retro-attribution command.** `AssignRevenueAttribution` is not created; mis-attribution is corrected by reverse-and-re-recognize | `B9_FIRST_TOUCH_MODEL.md` §7 |
| `B9-D-A025` | **No optimistic `version` on financial rows.** ADR-010 scopes it to *editable* resources; an immutable row carrying one would advertise editability. Reversal concurrency uses a row lock instead | `B9_IDEMPOTENCY_CONCURRENCY.md` §7 |
| `B9-D-A026` | **Money is exact decimal**: `NUMERIC(18,4)`, decimal-string on the wire, never binary float; `ROUND_HALF_UP` declared but never exercised in Phase 1; zero and negative amounts rejected | `B9_CURRENCY_MONEY_MODEL.md` §4 |
| `B9-D-A027` | **`RevenueEvent.status` is derived from the reversal folds** (both, per `B9-D-A034`), recomputed under the same row lock that writes the reversal, monotonic, never directly settable | `B9_REVENUE_EVENT_MODEL.md` §5 |
| `B9-D-A028` | **Two independent idempotency guards**: `(workspace_id, idempotency_key)` and the canonical source identity `(workspace_id, source_type, source_entity_type, source_public_id)` where not fully reversed. The second is what makes payment replay safe when a retry generates a fresh key | `B9_IDEMPOTENCY_CONCURRENCY.md` §1 |
| `B9-D-A029` | **Reconciliation detects; it never mutates financial truth.** Scans are read-only; a case resolution records a decision and may reference a command the operator ran separately under that command's own authority | `B9_RECONCILIATION_MODEL.md` §2 |
| `B9-D-A030` | **Revenue never requires Discovery.** Every provenance hop is optional and the first-touch resolver returns `NONE` rather than raising when both candidate sources are empty, so Track B produces valid financial truth with no Track-B entity existing | `B9_DUAL_TRACK_COMPATIBILITY.md` §3 |
| `B9-D-A031` | **Six new permissions**, with recognize/reverse/view separated and recognition stopping at `admin`; `analytics.view` reused verbatim, and required *conjunctively with* `revenue.view` wherever a monetary field is returned (`B9-D-A038`) | `B9_RBAC_TENANCY.md` §2-§3 |
| `B9-D-A032` | **Workspace scope comes only from the session**; no endpoint accepts `workspace_id`, and a public ID never authorizes access by itself. Cross-workspace references resolve `404`, never `403` | `B9_RBAC_TENANCY.md` §4 |
| `B9-D-A033` | **A reversal's `net` is derived, never supplied.** The caller sends `gross` only; B9 computes `Rn = ROUND_HALF_UP((Pg+Rg)×N/G, 4) − Pn` — a running-total allocation — under the event row lock. Supplying `net` is `B9-AF-035`. This is what makes gross exhaustion force net exhaustion instead of the two moving independently; the converse is `B9-D-A040` | `B9_REVERSAL_MODEL.md` §4 |
| `B9-D-A034` | **`status = 'reversed'` requires both folds exhausted**, `Σ gross = gross_amount` **AND** `Σ net = net_amount`. Gross-only status authority would mark an event fully reversed while net revenue survived on it — unreversible, and with its source released for re-recognition | `B9_REVENUE_EVENT_MODEL.md` §5 |
| `B9-D-A035` | **First-touch draws from two candidate sources, ordered as one set**: persisted `attribution_touchpoints` and derived `discovery_results` rows read from frozen B3. A single total order decides; an exact `occurred_at` tie goes to the explicitly recorded human fact | `B9_FIRST_TOUCH_MODEL.md` §2, §4 |
| `B9-D-A036` | **There is no system touchpoint writer.** `RecordTouchpoint` is human-only and `recorded_by_membership_id` is NOT NULL. Automatic Track-A attribution comes from *reading* B3's immutable provenance at recognition time — not from a background writer, a system actor, or an event subscription | `B9_ATTRIBUTION_MODEL.md` §2 |
| `B9-D-A037` | **Source identity is three separate things**: `source_ref` (always a registered §A workspace-scoped `EntityRef`), `origin_kind` (the acquisition channel), and `source_code` (a contract string such as a DiscoverySource code, never an `EntityRef`, never workspace-resolved). This keeps frozen registry §B and frozen B3 intact | `B9_ATTRIBUTION_MODEL.md` §4 |
| `B9-D-A038` | **Every response carrying a `Money` field requires `revenue.view`**, conjunctively with whatever else the operation needs. A broad `analytics.view` grant — which frozen B1 gives `member` and `viewer` — never becomes a finance-data grant | `B9_RBAC_TENANCY.md` §2a |
| `B9-D-A039` | **`currency` is an *optional* parameter on every operation returning a single-currency scalar, defaulting to the workspace's own presentation currency.** The frozen `AttributionReport` carries one `Money` and cannot be extended, so the request is constrained rather than the no-FX rule relaxed — but the constraint must not break the frozen parameterless `getAttribution`, whose frozen definition declares `"parameters": []`. The default is not invented: frozen `BACKEND_ANALYTICS_SEMANTICS.md` already designates the workspace/report currency, and frozen `B1_IDENTITY_DATA_MODEL.md` stores `workspaces.currency` NOT NULL default `SAR`. (`B9-FIX.1` made it *required*; `B9-FIX.2` corrected that as a breaking change to a frozen operation) | `B9_API_DTO_CONTRACTS.md` §3a |
| `B9-D-A040` | **Gross exhaustion implies net exhaustion; the converse does not.** The running-total derivation guarantees `Σ gross = G ⟹ Σ net = N`, but rounding can drive the net fold to `N` while a gross residual remains (reachable for any event with `G/N ≥ 2`). A reversal may therefore derive `net = 0` **only** as the *terminal gross-cleanup*: `Pg + Rg = G` **and** `Pn = N`. Every non-terminal zero-net reversal is `B9-AF-029`. Reversing the whole remaining gross always succeeds, so no event can be stranded | `B9_REVERSAL_MODEL.md` §4.1, §4.1a |
| `B9-D-A041` | **Reconciliation-resolution idempotency is durable and case-local.** `resolution_idempotency_key` + `resolution_request_hash` on `financial_reconciliation_cases`, written only on successful resolution and immutable thereafter, under `UNIQUE (workspace_id, resolution_idempotency_key) WHERE NOT NULL`. Same key + matching hash replays the stored outcome; same key + differing hash is `B9-AF-003`; a case has exactly one terminal resolution, so one key per case is the correct cardinality and no resolution-attempt table exists | `B9_IDEMPOTENCY_CONCURRENCY.md` §1, §2 |
| `B9-D-A042` | **Per-event `owner_ref` is display-only and live; `touchpoint_count` counts allocations and is derived from the snapshot.** Deal ownership is mutable and B6's, and no evidence requires historical owner attribution, so it is resolved at read time and never snapshotted into financial truth. `touchpoint_count` is the number of allocations the event received — `1` attributed, `0` unattributed in Phase 1 — matching the frontend's own `filter(item => item.touchpoint).length`, not a count of candidates considered | `B9_API_DTO_CONTRACTS.md` §2a |
| `B9-D-A043` | **The workspace presentation currency is resolved at REQUEST TIME, and it is mutable.** Frozen B1 types `WorkspaceDetail.currency` `(R,W)` and changes it via `UpdateWorkspace`, so B9 must not describe it as immutable. The omitted-`currency` default reads the workspace's *current* value when the request is served; it **selects** rows already in that currency and never converts. Changing the workspace currency therefore changes which currency the same parameterless report selects later, and no stored amount moves. An "as-of the period" resolution is rejected: neither B9 nor frozen B1 stores any temporal record of `workspaces.currency`, so it would have to invent a history or fall back on forbidden FX. Callers needing a period-stable currency pass `currency` explicitly | `B9_API_DTO_CONTRACTS.md` §3a.1; `B9_CURRENCY_MONEY_MODEL.md` §8a |
| `B9-D-A044` | **A `filtered = true` `discovery_results` row is NOT an eligible first-touch candidate.** Frozen B3 records it as retained audit evidence that a job observed a Business which then failed a **caller-supplied** post-filter, and excludes it from the job's visible result set, from `deduplicated_count`, and from the index B3 itself names *"the visible result set"*. B9 adopts B3's own visible/evidence line: an attribution winner must be an acquisition the workspace actually accepted, which is also what the frozen *"approved source identity"* clause requires. The rule only ever removes candidates, so its worst case is an unattributed event — never a moved or manufactured amount | `B9_FIRST_TOUCH_MODEL.md` §2.2, §2.2a |

`CLASS_A_DEFINED = 44`, `CLASS_A_UNRESOLVED = 0` — every decision above is **RESOLVED**, with a specific citation, in this pack. `B9-D-A033`…`B9-D-A039` were added by `B9-FIX.1`; `B9-D-A040`…`B9-D-A042` by `B9-FIX.2`, and `B9-D-A039` was **revised** by it. `B9-D-A043` and `B9-D-A044` were added by `B9-FIX.2a`, each closing a rule the pack relied on without ever stating — the resolution instant of a *mutable* workspace currency, and whether a filtered-out discovery observation may win an attribution. Each replaces something an earlier draft had left contradictory, undefined, or asserted without a mechanism — `B9-D-A040` a rounding edge asserted away as a biconditional, `B9-D-A041` a design specified in three documents but carried by no decision id, `B9-D-A042` two frontend fields no B9 operation returned.
