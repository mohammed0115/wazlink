# WazLink Public-ID Prefix Registry

> **B0 status:** Documentation and contracts only. This registry is normative for B1 Foundation/API references and does not implement ID generation.

## Authority and invariants

Every externally visible persistent resource uses an immutable opaque `public_id` with a registered prefix. Internal UUIDv7 identity remains the primary identity and is never replaced by, or exposed only as, the public ID. Prefixes are case-sensitive. A canonical persistent identifier is unique globally unless the resource row below explicitly says that its database uniqueness is workspace-scoped; API lookups always require workspace authorization.

The generation rule is `public_id = <PREFIX>-<opaque immutable token>`. The token is generated by the canonical UUIDv7/public-ID service, is not derived from display names or sequential UI fixtures, and is stored once at creation. Collision handling is a transactionally retried unique-constraint failure; the service generates a new opaque token and never mutates an existing public ID. Public IDs are immutable after creation.

### `AID-` cross-domain semantics

`AID-*` is referenced by two frontend correlation fields and by nothing else: `recommendationId` on an `AGA-*` agent action (`client/src/domain/sales-ai.js:150`) and `suggestionId` on `state.inboxAssistance` (`client/src/domain/sales-ai.js:171`). Both are **in-memory frontend correlation only**. Neither implies a Backend persistence contract, a foreign key, or an `EntityRef`.

`AID-` does not collide with `AGA-`/`RUN-` semantics and is not an alias for them: `AGA-` is a governed *agent action* resolved in section C to the canonical `RUN-*` AutomationRun, whereas `AID-` is the *advisory decision output* that an action may cite. A future backend AI-decision resource is not authorised by the presence of these references; it would require an ADR, a data-model change, a domain-ownership entry, and a newly approved prefix. Until then, implementation MUST NOT persist `AID-*`, MUST NOT mint a Backend public ID for it, and MUST NOT treat `recommendationId` as a resolvable public-ID reference. Where AI output must be retained, the existing `lead_intelligence_analyses`/`ai_usage_records` tables and the `AI content` data class in `BACKEND_PRIVACY_AND_DATA_HANDLING.md` govern it.

`Docs/reference/ENTITY_MODEL.md` describes a legacy V1 `CopilotDecisionRecord` with an `AID-####` prefix. That legacy document is **corroborating evidence only** and is not current normative B0 truth; the frozen frontend and this registry govern.

| `AUTORUN-` | `RUN-` | `{id:"AUTORUN-1001", automationRuleId, ruleNameSnapshot, status}` is an AutomationRun; `RUN-*` is canonical |

No C-class identifier is accepted as a new persistent public ID. Lookalike collisions are explicitly resolved: `TSK-` is Task and `TASK-` is its UI alias; `CONV-` is Conversation, `CON-` is Contact, and `COND-` is an automation condition fragment — all three are distinct and none may be substituted for another; `INV-` is a team-invitation fixture while `INV-BILL-` is the platform Invoice; `QRT-` is the Quick Reply Template messaging/UI fixture while `UPQ-` is the canonical persistent UpgradeQuote, and the two namespaces are disjoint and must never be substituted for one another; and `PIPE-` is the single canonical Pipeline prefix with no competing screen-fixture classification.

## Excluded non-identifier tokens

The reconstruction rule is mechanical and compound-aware: a token's prefix namespace is its **leading run of all-uppercase alphabetic segments**, and a token is an identifier only if at least one following segment is numeric. This yields `AGA-LOG-` from `AGA-LOG-8001` (never `LOG-`), `SIG-` from `SIG-1042-A`, `ACT-` from `ACT-1042-1`, and `INV-BILL-` from `INV-BILL-1001`.

#### Normative discovery procedure

Literal scanning alone is insufficient, because a namespace may exist only at runtime. B0-FIX.6 recovered `AUTOLOG-` and `AUTONOT-` this way but relied on a hardcoded generator-name list (`nextNumericId`/`s11Id`/`s11Audit`), which was itself incomplete and consequently missed `AID-`. **A hardcoded helper-name list is not an acceptable discovery rule.** Any reconstruction of the frozen-frontend namespace MUST instead apply all five of the following passes, in order, and take their union:

1. **Discover generator definitions structurally, by shape rather than by name.** A prefix generator is any function or helper whose body composes an identifier by interpolating or concatenating one of its own parameters immediately followed by `-` (for example a body matching `` `${prefix}-…` `` or `prefix + "-"`). Enumerate every such definition in the runtime tree; never assume the set is closed. Applying this to `30bc15e9ca3c0205df2b49e792fce1b8e78a36b1` yields exactly three definitions — `nextNumericId` (`client/src/domain/data.js:546`), `s11Id` (`client/src/domain/data.js:1014`), and `nextId` (`client/src/domain/sales-ai.js:23`) — plus one prefix-forwarding wrapper, `s11Audit` (`client/src/domain/data.js:1015`), which passes its own `prefix` parameter through to a discovered generator. Wrappers are discovered by the same shape test applied transitively.
2. **Enumerate every call-site of every generator and wrapper found in pass 1**, and read the literal prefix argument at the position that the definition forwards. This is the only pass that can see `AUTOLOG-`, `AUTONOT-`, and `AID-`, none of which appears as a literal anywhere in the frozen tree.
3. **Scan string literals** for tokens matching the compound-aware rule above.
4. **Scan template literals and string concatenations** for composed identifiers such as `` `CHK-${…}` ``, `` `REC-BUSINESS-${…}` ``, `` `EVT-LEGACY-${…}` ``, and `` `MANUAL-${…}` ``.
5. **Classify actual entity identities only.** A token qualifies only where it is used as an entity `id` or as a reference field. Enum values, catalog slugs, engine-version markers, CSS/test selectors, header names, locale tags, and timestamps are excluded and are listed below.

Every future audit and every future registry change MUST re-run all five passes against the frozen baseline. Adding a new frontend ID helper therefore cannot silently introduce an unclassified namespace, because pass 1 discovers helpers by shape and not from any list maintained in this document.

Applying that procedure to `30bc15e9ca3c0205df2b49e792fce1b8e78a36b1` yields **56 identifier prefixes**, every one of which is classified exactly once in section A, B, or C above. (B0-FIX.6 reported 55; that figure omitted `AID-` and is superseded by B0-FIX.7.)

## Cross-domain invariants

`BUS-*`, `LEAD-*`, `CONV-*`, and `DEAL-*` are resolved by typed public-ID references and workspace authorization, never by display name. `DEAL-*` does not imply `REV-*`; a `REV-*` exists only after the explicit revenue-recognition command. `ATT-*` is attribution metadata, never recognized-revenue amount truth, and cannot mutate `REV-*`. `SUB-*`, `UPQ-*`, `INV-BILL-*`, `PAY-*`, and `TAX-*` are Platform Billing/Tax identities and are not customer CRM revenue identities. An `UPQ-*` UpgradeQuote is platform commercial authorization only; it never creates, implies, or mutates a `REV-*` RevenueEvent. Any new canonical prefix requires an ADR update, API/DTO update, index update, and traceability entry before implementation.
